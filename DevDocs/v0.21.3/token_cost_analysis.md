# 专项分析 — Idle Wakeup Token 成本与商业化唤醒间隔建议

> **状态**：分析稿  
> **关联版本**：`v0.21.3`  
> **关联文档**：`PRD.md`、`solution.md`、`DevDocs/feature-design/IdleWakeup.md`  
> **最后更新**：2026-06-18

---

## 1. 结论摘要

在当前 Agent 架构下，Idle Wakeup 并不是只消耗一条很短的 `<空闲感知>` 文本。一次唤醒触发 LLM 时，请求中通常还包含：

- system prompt；
- RAG 注入的事实 / 情景 / 动作技能摘要；
- 动态裁剪后的最近消息上下文；
- **完整工具 schema**，当前约 **8423 tokens**；
- 本次 `<空闲感知>` 消息；
- 可能的后续工具调用与二次 LLM 调用。

根据现有样例 prompt 与当前工具列表估算：

| 场景 | 估算输入 tokens | 估算补全 tokens | 单次成本，不考虑缓存 | 单次成本，大量工具/schema 命中缓存时 |
|------|----------------:|----------------:|----------------------:|--------------------------------------:|
| 轻量空闲唤醒，Agent 只心理活动 / 等待 | 9k~12k | 100~300 | 约 ¥0.018~¥0.024 | 约 ¥0.001~¥0.004 |
| 普通空闲唤醒，带少量历史和事件摘要 | 11k~16k | 200~600 | 约 ¥0.022~¥0.033 | 约 ¥0.003~¥0.008 |
| 唤醒后 Agent 调用工具，产生二次 LLM | 20k~35k | 300~1000 | 约 ¥0.04~¥0.07 | 约 ¥0.006~¥0.02 |

若以商业游戏、且 token 费用由玩家承担为前提，默认 **2~5 分钟** 会偏激进。更推荐：

> **商业默认：10~15 分钟随机唤醒一次。**

可选模式：

| 模式 | 建议随机区间 | 适用场景 |
|------|--------------|----------|
| 开发 / 演示模式 | 2~5 分钟 | 便于观察功能是否生效 |
| 商业默认模式 | 10~15 分钟 | 玩家付费、控制后台消耗 |
| 高活跃陪伴模式 | 5~10 分钟 | 玩家明确选择高频陪伴或愿意承担成本 |
| 省钱 / 低功耗模式 | 15~30 分钟 | 长时间挂机、多人 Agent、移动端或云成本敏感 |

本分析建议：`solution.md` 中默认配置可保持 2~5 分钟用于当前开发验证，但在商业化配置中应改为 **10~15 分钟**，或至少提供“开发 / 商业 / 省钱”三档配置。

## 2. 当前上下文裁剪逻辑确认

### 2.1 不是简单保留 20 条消息

`agent_interuptible.py` 中仍保留：

```python
MAX_CONTEXT_SIZE = 20

def _filter_messages(messages, k=20):
    messages = messages[-k:]
    return messages
```

但这段当前只用于废弃的 `chain`：

```python
chain = (
    RunnablePassthrough.assign(messages=lambda x: _filter_messages(x["messages"], k = MAX_CONTEXT_SIZE))
    | prompt_template
    | llm_with_tools
)
```

真实生产路径在 `chatbot(state)` 中：

```python
system_tokens = await estimate_system_prompt_tokens(prompt_template, system_vars)
tools_tokens = get_tools_token_count(tools)
trimmed_messages = trim_messages_by_token(
    messages=state['messages'],
    system_prompt_tokens=system_tokens,
    tools_token_count=tools_tokens,
)

prompt = await prompt_template.ainvoke({
    "messages": trimmed_messages,
    **system_vars
})
response = await llm_with_tools.ainvoke(prompt)
```

因此真实上下文裁剪依据是 `trim_messages_by_token(...)`，不是固定最近 20 条。

### 2.2 实际 token 预算公式

`prompt_utils.py` 中：

```python
max_context = int(os.getenv("AGENT_MAX_CONTEXT_TOKENS", "128000"))
reserve_ratio = float(os.getenv("CONTEXT_RESERVE_RATIO", "0.85"))
output_reserve = int(os.getenv("OUTPUT_RESERVE_TOKENS", "4096"))

budget = int(max_context * reserve_ratio) - system_prompt_tokens - tools_token_count - output_reserve
```

默认值下：

```text
max_context = 128000
reserve_ratio = 0.85
output_reserve = 4096
```

即：

```text
可用于 messages 的预算 ≈ 128000 * 0.85 - system_tokens - tools_tokens - 4096
```

以当前测得工具 schema 约 8423 tokens、样例 system 约 602 tokens 估算：

```text
messages 预算 ≈ 108800 - 602 - 8423 - 4096 ≈ 95679 tokens
```

这意味着在默认配置下，普通对话历史基本不会被裁剪，除非累计历史非常长。

### 2.3 prompt 日志可能高估或低估真实请求

当前 `_save_prompt_log(state, curtime)` 在 `save_memory` 节点执行，并且注释写明：

```python
# 用全量 state['messages'] 重新渲染完整 prompt
```

它使用的是：

```python
prompt = await prompt_template.ainvoke({
    "messages": state['messages'],
    ...
})
```

所以日志文件展示的是完整 state messages 渲染结果，不一定等于 `chatbot()` 中传给 LLM 的 `trimmed_messages`。

但在默认 128k 上下文预算下，样例日志规模很小，不会触发裁剪，因此样例日志对当前阶段仍有参考价值。

参考日志：

```text
Src/PythonServer/logs/prompts/小明/2026-06-18_11-33-19.log
```

使用 `tiktoken cl100k_base` 对日志文本估算：

| 部分 | blocks | 字符数 | tokens |
|------|-------:|-------:|-------:|
| System Message | 1 | 844 | 602 |
| Human Message | 1 | 560 | 493 |
| AI Message | 7 | 1713 | 907 |
| Tool Message | 6 | 344 | 227 |
| 整个日志 | - | 4676 | 2309 |

另外，当前生产工具列表：

```text
tools_count = 28
tools_tokens ≈ 8423
```

因此，如果某次请求上下文接近该日志规模，则 LLM 请求输入大致为：

```text
日志消息与 system 等 ≈ 2309 tokens
工具 schema ≈ 8423 tokens
合计 ≈ 10732 tokens
```

再考虑 provider 消息包装开销、RAG 内容变化、空闲事件摘要、历史更长等因素，实际可按以下区间估算：

```text
轻量：9k~12k input tokens
普通：11k~16k input tokens
较重：20k~35k input tokens（通常因为唤醒后又调用工具并二次 LLM）
```

## 4. 价格参数

按用户给定 deepseek-v4-pro 价格：

| 类型 | 价格 |
|------|------:|
| 输入 | ¥1.8900 / 1M tokens |
| 补全 | ¥3.7800 / 1M tokens |
| 缓存读取 | ¥0.0160 / 1M tokens |

计算公式：

```text
输入成本 = input_tokens / 1_000_000 * 1.89
补全成本 = output_tokens / 1_000_000 * 3.78
缓存读取成本 = cached_tokens / 1_000_000 * 0.016
```

## 5. 单次 Idle Wakeup 成本估算

### 5.1 不考虑缓存

| 输入 tokens | 补全 tokens | 输入成本 | 补全成本 | 单次合计 |
|------------:|------------:|---------:|---------:|---------:|
| 9,000 | 100 | ¥0.0170 | ¥0.0004 | ¥0.0174 |
| 12,000 | 300 | ¥0.0227 | ¥0.0011 | ¥0.0238 |
| 16,000 | 600 | ¥0.0302 | ¥0.0023 | ¥0.0325 |
| 25,000 | 800 | ¥0.0473 | ¥0.0030 | ¥0.0503 |
| 35,000 | 1,000 | ¥0.0662 | ¥0.0038 | ¥0.0699 |

粗略记忆：

```text
一次轻量唤醒 ≈ ¥0.02
一次普通唤醒 ≈ ¥0.02~¥0.03
唤醒后调用工具并继续推理 ≈ ¥0.04~¥0.07
```

### 5.2 考虑缓存读取

如果 provider 对工具 schema / system prompt 等重复前缀命中缓存，则成本会明显降低。假设：

```text
cached_tokens = 8k~10k
non_cached_input = 1k~6k
output = 100~600
```

| 缓存 tokens | 非缓存输入 tokens | 补全 tokens | 缓存成本 | 非缓存输入成本 | 补全成本 | 单次合计 |
|------------:|------------------:|------------:|---------:|---------------:|---------:|---------:|
| 8,000 | 1,000 | 100 | ¥0.00013 | ¥0.00189 | ¥0.00038 | ¥0.00240 |
| 9,000 | 3,000 | 300 | ¥0.00014 | ¥0.00567 | ¥0.00113 | ¥0.00694 |
| 10,000 | 6,000 | 600 | ¥0.00016 | ¥0.01134 | ¥0.00227 | ¥0.01377 |

但注意：

- 不能假设所有请求都稳定命中缓存；
- 工具 schema 是否以 provider 可缓存前缀形式复用，取决于 API 与请求结构；
- RAG 内容、消息历史和空闲摘要会变化；
- 商业定价最好按“不考虑缓存”或“部分缓存”保守估计。

## 6. 不同唤醒间隔的成本估算

以下按“每次轻量 / 普通唤醒不考虑缓存约 ¥0.02~¥0.03”估算。

### 6.1 单 Agent 每小时成本

| 随机区间近似 | 平均间隔 | 每小时次数 | ¥0.02/次 | ¥0.03/次 | ¥0.05/次 |
|--------------|---------:|-----------:|---------:|---------:|---------:|
| 2~5 分钟 | 3.5 分钟 | 17.1 次 | ¥0.34/h | ¥0.51/h | ¥0.86/h |
| 5~10 分钟 | 7.5 分钟 | 8.0 次 | ¥0.16/h | ¥0.24/h | ¥0.40/h |
| 10~15 分钟 | 12.5 分钟 | 4.8 次 | ¥0.10/h | ¥0.14/h | ¥0.24/h |
| 15~30 分钟 | 22.5 分钟 | 2.7 次 | ¥0.05/h | ¥0.08/h | ¥0.13/h |
| 30~60 分钟 | 45 分钟 | 1.3 次 | ¥0.03/h | ¥0.04/h | ¥0.07/h |

### 6.2 单 Agent 每 100 小时成本

| 随机区间 | ¥0.02/次 | ¥0.03/次 | ¥0.05/次 |
|----------|---------:|---------:|---------:|
| 2~5 分钟 | ¥34.29 | ¥51.43 | ¥85.71 |
| 5~10 分钟 | ¥16.00 | ¥24.00 | ¥40.00 |
| 10~15 分钟 | ¥9.60 | ¥14.40 | ¥24.00 |
| 15~30 分钟 | ¥5.33 | ¥8.00 | ¥13.33 |
| 30~60 分钟 | ¥2.67 | ¥4.00 | ¥6.67 |

### 6.3 多 Agent 成本线性放大

如果同一玩家场景里同时有多个自主 Agent，空闲唤醒成本近似线性放大：

```text
总成本 ≈ 单 Agent 成本 × Agent 数量
```

例如 3 个 Agent，10~15 分钟区间，按 ¥0.03/次估算：

```text
单 Agent ≈ ¥0.14/h
3 Agent ≈ ¥0.43/h
100 小时 ≈ ¥43.2
```

因此商业化时必须明确：

- 玩家是否只承担主伙伴 Agent 的费用；
- 后台 NPC 是否使用更低频率或非 LLM 模拟；
- 多 Agent 是否共享唤醒调度或分批唤醒。

## 7. 玩家付费可接受性判断

### 7.1 2~5 分钟默认值的问题

2~5 分钟用于开发验证很合适，因为能较快看到 Agent 自主醒来。但商业默认下存在问题：

- 玩家挂机 1 小时，即使什么也不做，单 Agent 也可能消耗约 ¥0.34~¥0.51；
- 100 小时游戏时长，单 Agent 可能消耗 ¥34~¥51；
- 如果唤醒后经常调用工具并二次推理，成本可能更高；
- 多 Agent 会线性放大。

如果商业模式要求玩家直接承担 token 费用，这个默认频率很容易被玩家感知为“后台一直扣费”。

### 7.2 更合理的商业默认

比较稳妥的商业默认是：

```text
10~15 分钟随机唤醒一次
```

原因：

- 单 Agent 每小时约 4.8 次；
- 不考虑缓存，约 ¥0.10~¥0.14/h；
- 100 小时约 ¥9.6~¥14.4；
- 如果缓存命中较好，实际可能低很多；
- 玩家能感知到角色“偶尔会自主醒来”，但不会频繁后台消耗。

如果游戏强调 AI 陪伴、玩家明确选择高活跃模式，可以提供：

```text
5~10 分钟
```

但应在 UI 上说明成本更高。

如果是普通商业游戏、玩家主要为剧情 / 玩法付费，而不是为 AI 陪伴付费，建议提供：

```text
15~30 分钟省钱模式
```

### 7.3 推荐配置分档

建议 `idle_wakeup.json` 未来支持 profile，或至少在配置注释 / 文档中约定：

| 档位 | 随机区间 | 说明 |
|------|----------|------|
| `dev` | 120~300 秒 | 开发调试，快速观察功能 |
| `active` | 300~600 秒 | 高活跃陪伴，玩家愿意承担更高成本 |
| `commercial_default` | 600~900 秒 | 商业默认推荐 |
| `saving` | 900~1800 秒 | 省钱 / 低功耗 / 多 Agent 场景 |

当前 v0.21.3 若仍处于开发验证阶段，可以先实现 120~300 秒默认；但在进入商业测试前，应把默认配置改成 600~900 秒。

## 8. 对 v0.21.3 方案的建议调整

基于成本分析，建议 `solution.md` 采用以下表述：

- 开发验证默认：`delay_min_seconds=120`，`delay_max_seconds=300`；
- 商业推荐默认：`delay_min_seconds=600`，`delay_max_seconds=900`；
- 在 `idle_wakeup.json` 中显式标注当前使用的是开发验证默认，避免未来误带入商业环境。

如果当前项目目标是先验证游戏机制，则保留 2~5 分钟可以接受。

如果目标是模拟商业上线配置，则应直接改为 10~15 分钟。

## 9. 降低成本的后续优化方向

这些优化不建议放入 v0.21.3 初版，但应作为后续方向：

1. **空闲唤醒分级**
   - 第一次空闲 5~10 分钟；
   - 连续无动作后退避到 15~30 分钟。

2. **无事件不唤醒或更低频唤醒**
   - 如果 WorldEventLog 摘要为空，可只做计时续约，不触发 LLM；
   - 或把无事件唤醒间隔拉长到 30~60 分钟。

3. **限制唤醒后工具链深度**
   - 空闲唤醒 prompt 中强调“可以选择继续等待”；
   - 避免 Agent 每次醒来都 observe / get_world_event_log。

4. **工具 schema 成本优化**
   - 当前工具 schema 约 8423 tokens；
   - 可研究按场景 / 能力分组绑定工具，降低每次请求固定输入成本。

5. **多 Agent 分批唤醒**
   - 不让多个 Agent 同时 idle wakeup；
   - 对后台 NPC 使用更低频策略。

---

## 10. 最终建议

当前机制验证阶段：

```text
2~5 分钟可以接受，便于观察功能是否工作。
```

商业游戏、玩家承担 token 费用时：

```text
默认建议 10~15 分钟。
```

如果游戏中同时有多个 Agent，或者玩家对后台扣费敏感：

```text
默认建议 15~30 分钟，并提供高活跃模式给愿意承担成本的玩家。
```

不要把 2~5 分钟作为商业默认，除非产品明确定位为高频 AI 陪伴，且 UI / 计费说明让玩家知道后台自主行为会持续消耗 token。
