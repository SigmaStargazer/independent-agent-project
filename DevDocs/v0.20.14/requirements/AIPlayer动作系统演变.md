# AIPlayer 动作系统演变

## 概述

AIPlayer 的动作系统经历了三代演进，每一代解决的核心问题不同，但设计哲学一脉相承：**让 Agent 的行为越来越连续、越来越自主，减少对 LLM 的依赖频次**。

---

## 第一代：单步 Action

### 架构

```
LLM 每次决策 → 发出1个动作 → Unity执行 → 返回结果 → LLM 再次决策 → ...
```

Agent 可用的动作工具：

| 工具 | 说明 |
|------|------|
| `move_cmd` | 向指定方向移动指定距离 |
| `interact_cmd` | 与身旁对象交互 |
| `select_cmd` | 选择选项 |
| `input_cmd` | 输入文本 |

### 运行方式

每个动作是**一次独立的 LLM 工具调用**。Agent 完成一个动作后，必须停下来观察环境，等 LLM 根据新的环境信息发出下一个动作指令。

### 典型交互流程

以"走到拉杆旁并拉拉杆"为例：

```
1. LLM: move_cmd(right, 2.43)     → 向右走2.43米到拉杆旁
   Unity执行...返回结果
2. LLM: observe_cmd()             → 观察环境，确认到了拉杆旁
   Unity执行...返回环境信息
3. LLM: interact_cmd()            → 拉拉杆
   Unity执行...返回结果
```

### 核心问题

**两个动作之间必定插入一个完整的 LLM 推理周期**（输入处理 → 模型推理 → 输出解析），导致：

- **动作失去连续性**：本应是连贯的"走过去→拉拉杆"，被拆成3轮LLM调用，中间有数秒空白
- **浪费 token**：每轮都要把完整上下文喂给 LLM，大量重复
- **浪费时间**：LLM 推理延迟（通常2-5秒）叠加在每步之间
- **体验割裂**：Agent 看起来像一个每次只能想一步的笨拙角色

### 设计隐喻

像一个人每迈一步都要停下来重新思考下一步怎么走——不是因为不会走，而是因为"运动系统"和"决策系统"之间没有缓冲。

---

## 第二代：Action Sequence

### 解决的问题

**消除同一任务内多个动作之间的 LLM 介入**。让 Agent 一次性规划出多步动作，交给执行引擎自主连续执行。

### 架构

```
LLM 一次性规划 → 发出N个动作的序列 → Unity逐帧执行，condition满足自动推进 → 全部完成后通知LLM
```

### 核心设计

#### 两类 Action

| 基类 | 适用场景 | condition | Unity 执行模式 |
|------|----------|-----------|----------------|
| `StateChangeAction` | 持续进行，靠 condition 结束（wait、move） | **必填**，Pydantic 校验 | 每帧 ConditionEvaluator.Evaluate + FSM 状态 |
| `BaseAction` | 一次完成（interact、select、input） | 无 | 执行一次 → OnActionFinished |

#### Condition 系统

每个持续型动作有一个**结束条件**（condition），是一个 DynamicExpresso 表达式，Unity 侧每帧求值：

```
可用变量：
- myself:         Agent自身数据（Position, Velocity, State）
- objects[i]:     场景物体数据（Position, Velocity, State）
- displacement:   当前动作开始至今的横向位移
- actionTime:     当前动作开始至今所经过的时间
- canInteract:    周围是否有可交互物体
- nearestInteractableIndex: 最近可交互物体序号
```

#### 三步流程

```
1. plan_action_sequence_cmd    → 规划序列（Unity校验condition合法性）
2. start_action_sequence_cmd   → 确认开始执行
3. [执行中] continue_action_sequence_cmd  → 中断后继续（如需）
```

### 典型交互流程

同样的"走到拉杆旁并拉拉杆"：

```
1. LLM: plan_action_sequence_cmd([
     {"action": "move", "direction": "right", "condition": "canInteract == true && nearestInteractableIndex == 4"},
     {"action": "interact"}
   ])
2. LLM: start_action_sequence_cmd()
   Unity自主执行：走到拉杆旁(每帧判定condition) → 拉拉杆 → 完成
3. 系统通知Agent：动作序列执行完成
```

**从3轮LLM调用降到1轮**，动作之间零延迟。

### 运行时数据流

```
LLM 输出 ActionStep JSON
  → Pydantic 校验
    → build_pb_action_step 序列化
      → protobuf 传给 Unity
        → AIPlayer.PlanActionSequence
          → ConditionEvaluator.ValidateAll 校验
            → StartActionSequence
              → ExecuteCurAction (每帧循环)
                → condition满足 → 推进到下一步
                → 全部完成 → SendFeedbackToAgent 通知Python侧
```

### 仍存在的问题

Action Sequence 解决了**同一任务内**动作的连续性，但**跨任务**的连续性仍然依赖 LLM：

```
LLM规划: [走到拉杆旁, 拉拉杆]  → 执行完成 → LLM再次规划: [走上浮板] → 执行完成 → LLM再次规划: [等浮板到对岸] → ...
```

每次"任务切换"都需要 LLM 重新决策。对于"坐浮板过河"这种需要**多阶段协调**的行为（等浮板→上浮板→等浮板到对岸→下浮板→走到门口），LLM 每次只规划当前阶段的序列，无法一次性规划出跨阶段的完整流程。

**根因**：LLM 缺乏经验，不知道"过河"这个意图应该展开为5步序列。`plan_action_sequence_cmd` 的 docstring 中虽然提供了少量场景示例，但这是开发者硬编码的，不是 Agent 通过经验积累动态掌握的。

### 设计隐喻

像一个人学会了连续走路（不再每步都停下来思考），但到了路口还是不知道该往哪拐——因为缺乏"从A到B的完整路线"的经验。

## 第三代：Action Skill

### 解决的问题

**消除跨任务规划对 LLM 的依赖**。让 Agent 通过经验积累掌握"完整的多阶段行为模式"，一次性输出覆盖全流程的 action_sequence。

### 核心洞察

Action Sequence 的执行引擎**已经具备自主完成多阶段行为的能力**——只要 LLM 能一次性规划出完整序列。问题不在执行层，而在规划层：**LLM 缺乏经验**。

Action Skill 的本质不是新增执行能力，而是给 LLM 一个**经验记忆系统**，让它从"每次从零规划"进化为"识别场景→调用经验→参数化执行"。

### 架构

```
┌─────────────────────────────────────────────────────┐
│  LLM 决策层                                          │
│  输入：环境消息 + <动作技能索引>（渐进式披露）          │
│  职责：理解意图 → 识别场景 → 选择技能 → 参数化模板     │
│  输出：完整的 action_sequence（覆盖全流程）            │
└──────────────────┬──────────────────────────────────┘
                   │
     ┌─────────────┼─────────────┐
     │             │             │
     ▼             ▼             ▼
┌─────────┐ ┌───────────┐ ┌──────────────┐
│ 技能学习 │ │ 技能使用   │ │ 技能精进     │
│ (Save)  │ │ (Load)    │ │ (Refine/Del) │
└─────────┘ └─────┬─────┘ └──────────────┘
                   │
                   ▼
┌─────────────────────────────────────────────────────┐
│  Action Sequence 执行引擎（第二代，无需改动）          │
└─────────────────────────────────────────────────────┘
```

### 三层机制

#### 1）技能学习：save_action_skill

Agent 成功完成一组动作序列后，主动将其保存为可复用模板：

- 从成功经验中提取，而非凭空编写
- 保存时将具体参数改为占位符（如 `{platform_idx}` 代替具体序号 `0`）
- per-agent 存储，每个 Agent 的技能库独立
- 创建时注入默认技能（与关卡配置绑定）

#### 2）技能使用：load_action_skill（渐进式披露）

**第一层**：System Prompt 常驻技能索引（轻量，每条一行）

```
<动作技能索引>
1. [坐浮板过河] 当需要乘坐移动平台越过深渊到达对岸时
2. [推箱子垫脚] 当需要用箱子垫高来到达高处时
</动作技能索引>
```

**第二层**：LLM 判断匹配后，调用 `load_action_skill` 加载完整模板

**第三层**：LLM 根据当前环境数据参数化模板，必要时微调，然后通过 `plan_action_sequence_cmd` 下发

**为什么用渐进式披露而非语义检索**：主 LLM 拥有最完整上下文（环境+对话+历史），是做"该用哪个技能"判断的最佳决策者。语义相似≠场景适用，向量数据库或小模型反而判断质量更低。

#### 3）技能精进：refine / delete

- 执行模板失败 → LLM 反思后 refine_action_skill
- 多次使用后发现更优写法 → refine_action_skill
- 模板长期未用或无法修复 → delete_action_skill

### 典型交互流程

**首次遇到浮板过河（无技能）**：

```
1. 玩家: "送我过去"
2. LLM: 自主规划 [走到拉杆旁, 拉拉杆]  → 执行完成
3. 玩家: "到浮板上"（需要提示，因为LLM只规划了一步）
4. LLM: 自主规划 [走上浮板]  → 执行完成
5. ...（多次交互，最终完成过河）
6. LLM: save_action_skill("坐浮板过河", 完整5步模板)  ← 经验总结
```

**再次遇到浮板过河（有技能）**：

```
1. 玩家: "送我过去"
2. LLM: 看到<动作技能索引>中匹配"坐浮板过河"
3. LLM: load_action_skill("坐浮板过河")  → 获取完整5步模板
4. LLM: 参数化模板（填入当前环境的物体序号、方向等）
5. LLM: plan_action_sequence_cmd(完整5步序列)
6. Unity自主执行：等浮板→上浮板→等浮板到对岸→下浮板→走到门口
7. 系统通知：动作序列执行完成
```

**从N轮LLM调用降到1轮**，全程零玩家提示。

### 设计隐喻

像一个人第一次走某条路需要导航（逐步提示），但走过一次后记住了完整路线，下次就能一气呵成走完——不是运动能力变了，而是**经验**变了。

---

## 三代对比总结

| 维度 | 单步 Action | Action Sequence | Action Skill |
|------|------------|-----------------|--------------|
| **解决的问题** | 基础动作能力 | 同任务内动作连续性 | 跨任务规划完整性 |
| **LLM调用频次** | 每步1次 | 每任务1次 | 每意图1次 |
| **动作间延迟** | 2-5秒（LLM推理） | 0（引擎自主推进） | 0（引擎自主推进） |
| **规划能力** | 单步 | 单任务多步 | 跨任务多阶段 |
| **经验依赖** | 无 | 无（docstring硬编码示例） | 有（动态学习+精进） |
| **玩家体验** | 每步都要提示 | 每任务要提示 | 首次可能需提示，后续自主 |
| **新增基础设施** | — | Unity执行引擎+Condition系统 | 技能存储+渐进式披露 |
| **类比** | 每步停下来思考 | 学会连续走路 | 记住完整路线 |

### 演变主线

```
动作粒度：  细 ←————————————→ 粗
            单步    动作序列    行为模式
LLM角色：   每步决策  每任务决策   意图决策+经验匹配
自主性：    低        中          高
```

每一代都没有推翻前一代，而是在前一代基础上叠加新层：

- **Action Sequence 复用了单步 Action 的所有动作类型**（move、interact、select、input），只是把它们串成序列
- **Action Skill 复用了 Action Sequence 的完整执行引擎**，只是给 LLM 加了经验记忆来改善规划质量

这就是三层架构的本质：

```
决策层（LLM）：  "做什么" ——— 越来越少介入
行为层（Skill）： "怎么做" ——— 经验驱动的规划模板
运动层（Seq）：   "执行"   ——— 每帧自主推进，无需等待
```
