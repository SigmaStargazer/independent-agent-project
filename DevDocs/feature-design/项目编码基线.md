# 项目编码基线（Project Encoding Baseline）

> 状态：长期有效
> 适用范围：含中文文案的 Unity（C#）/ Python / Protobuf / Markdown 混合项目
> 最后更新：2026-06-30
> 立项版本：v0.22.0

---

## 1. 为什么有这份文档

Windows 中文环境下，VS2022 / VSCode 等 IDE 在打开未带 BOM 的文本文件时，会先尝试 UTF-8，**解码失败回退到系统 ANSI（GBK / CP936）**。这意味着：

- 一个本来是 UTF-8 的文件，被在中文 Windows 上保存过一次后，可能悄无声息退化为 GBK。
- IDE 自身因为 fallback 看上去正常；但 Unity Inspector、Roslyn 编译期、Linux 工具链、Git diff 等**固定按 UTF-8 解析**的环境会出现 `��`、字符串截断、`Invalid character` 等。
- `.editorconfig` 的 `charset = utf-8` 只对**新建文件**生效，不会自动修复历史文件、也不阻止 IDE 以 GBK 重新保存。

本基线把"项目从一开始就强制 UTF-8、且不会被悄悄回退"作为基础设施统一沉淀。新项目按本文件初始化即可。

## 2. 编码基线五件套

| 文件 | 作用 |
|---|---|
| `.editorconfig` | 声明所有文本文件 `charset = utf-8`，新建文件遵循 |
| `.gitattributes` | `* text=auto` 统一换行符策略，避免转换时换行符误改 |
| `.vscode/settings.json` | VSCode `files.encoding=utf8` + `files.autoGuessEncoding=false`，避免 VSCode 在 Windows 上误猜 GBK |
| `Tools/check_file_encoding.py` | 全仓 / staged 编码自检 + 可选 `--fix` 自动从 GBK 转 UTF-8 |
| `Tools/hooks/pre-commit` + `Tools/enable_hooks.{sh,cmd}` | 本地 git pre-commit 拦截 GBK 提交；一行启用脚本 |

各文件全文以本仓库为准，下面是关键点。

### 2.1 `.editorconfig`

```ini
root = true

[*]
charset = utf-8
end_of_line = lf
insert_final_newline = true
trim_trailing_whitespace = true

[*.{cs,csx}]
charset = utf-8
indent_style = space
indent_size = 4

[*.{py,pyi}]
charset = utf-8
indent_style = space
indent_size = 4

[*.md]
trim_trailing_whitespace = false

[*.{cmd,bat}]
end_of_line = crlf
```

> 注：Unity C# 工程历史上一直 CRLF，本仓库 `.gitattributes` 没有强制 `eol=lf`，由 IDE 与 git 自适应。

### 2.2 `.gitattributes`

```gitattributes
* text=auto

*.cs     text diff=csharp
*.py     text diff=python
*.md     text diff=markdown
*.proto  text
*.json   text
*.txt    text
*.yml    text
*.yaml   text
*.cmd    text eol=crlf
*.bat    text eol=crlf
```

### 2.3 `.vscode/settings.json`

```json
{
  "files.encoding": "utf8",
  "files.autoGuessEncoding": false,
  "[csharp]": { "files.encoding": "utf8" },
  "[python]": { "files.encoding": "utf8" }
}
```

### 2.4 `Tools/check_file_encoding.py`

判定流程：

1. UTF-8（含 BOM 与无 BOM）解码成功 → `OK` / `UTF8-BOM`。
2. UTF-8 失败、GBK 解码成功 → `GBK`（嫌疑，可自动转换）。
3. 两者都失败 → `UNKNOWN`（永不自动改，需人工确认）。

常用调用：

```bash
# 默认范围检查（不含 ShootingEditor2D 旧场景、不含 Python 业务源码）
python Tools/check_file_encoding.py

# 检查指定目录、指定扩展名
python Tools/check_file_encoding.py path/to/dir --ext .cs,.md --verbose

# 一次性把 GBK 嫌疑文件转 UTF-8（保留 CRLF / 不写 BOM）
python Tools/check_file_encoding.py path/to/dir --ext .cs --fix

# pre-commit 用法（仅看 staged 文件）
python Tools/check_file_encoding.py --staged
```

默认扫描范围、默认扩展名、默认排除目录见脚本内 `DEFAULT_PATHS / DEFAULT_EXTS / DEFAULT_EXCLUDES`。**移植到新项目时，根据该项目实际目录结构调整这三个常量**。

### 2.5 `Tools/hooks/pre-commit` + `Tools/enable_hooks.{sh,cmd}`

pre-commit 脚本仅一行：

```bash
python "$ROOT/Tools/check_file_encoding.py" --staged
```

启用：

```bash
# Git Bash / Linux / macOS
bash Tools/enable_hooks.sh

# Windows CMD / PowerShell
Tools\enable_hooks.cmd
```

效果：`git config core.hooksPath` 被设为 `Tools/hooks`。之后 `git commit` 会先跑编码检查；任意 staged 文件非 UTF-8 即拒绝并打印修复命令。

关闭：

```bash
git config --unset core.hooksPath
```

## 3. 新项目初始化步骤

1. 把上述五件套复制到新仓库。
2. 在新仓库根执行：

   ```bash
   bash Tools/enable_hooks.sh   # 或 Windows: Tools\enable_hooks.cmd
   ```

3. 调整 `Tools/check_file_encoding.py` 中三个常量以匹配新项目目录结构。
4. 跑一次全量扫描：

   ```bash
   python Tools/check_file_encoding.py
   ```

   若出现 `GBK 嫌疑` 文件，运行 `--fix`；若出现 `未知` 文件，逐文件人工确认并转换。
5. 把上述检查整理为 README / CONTRIBUTING 的"克隆后第一步"提示，让团队成员知道要执行 `enable_hooks`。

## 4. Windows 中文环境注意事项

- **VS2022**：新建文件默认编码受 Windows 系统 Active Code Page 影响；中文 Windows 默认 CP936。务必：
  - 「文件 → 高级保存选项」检查并改为 `Unicode (UTF-8 without signature) - Codepage 65001`。
  - 在「工具 → 选项 → 文本编辑器 → 高级」中将默认保存编码改为 UTF-8 无 BOM（可用扩展或注册表设置）。
- **VSCode**：本基线已通过 `.vscode/settings.json` 锁死。注意检查"重新打开方式 → 选择编码"不要点错。
- **Git Bash / WSL / Linux / macOS**：默认 UTF-8，正常使用即可。
- 若执行 `python Tools/check_file_encoding.py` 控制台输出仍出现乱码（中文显示为问号），脚本内部已用 `sys.stdout.reconfigure(encoding="utf-8")` 兜底；如仍不行，临时设 `PYTHONIOENCODING=utf-8`。

## 5. 典型故障与排查

| 现象 | 排查 |
|---|---|
| Unity Inspector 中文显示为 `��` 或 `�����豸��Ϣ` | 文件被以 GBK 保存。运行 `python Tools/check_file_encoding.py --fix <path>` |
| Roslyn 编译报 `Character literal must contain exactly one character` 等莫名错误，定位行实际正常 | 该文件可能是 UTF-8 BOM 或残留控制字符；用脚本扫一遍 |
| 脚本判 `UNKNOWN` | 文件可能是 UTF-16 / 二进制 / 损坏。用 `file <path>` 进一步分析；不要 `--fix`，人工恢复 |
| `pre-commit` 没有触发 | 确认 `git config --get core.hooksPath` 输出 `Tools/hooks`；hook 文件可执行（Linux 上需 `chmod +x`） |
| 启用 hook 后正常 commit 也很慢 | `--staged` 模式只扫 staged 文件；若仍慢，检查 staged 文件数量与脚本扫描扩展名是否过宽 |

## 6. 与本仓库 v0.22.0 的范围差异

本仓库当前实现的默认值：

- `DEFAULT_PATHS` 包含 `Src/IndependentAgentProject/Assets/Scripts/IndependentAgentProject`、`Tools`、`DevDocs`、`Doc`、`AGENTS.md`、`README.md`。
- `DEFAULT_EXTS` 不含 `.py`（本仓库 Python 业务源码暂未纳入治理，等后续版本另立专题）。
- `DEFAULT_EXCLUDES` 默认排除 `Src/IndependentAgentProject/Assets/Scripts/ShootingEditor2D`（旧场景，遗留无关）、`Src/PythonServer`（业务目录暂不纳入）。

迁移到新项目时通常需要**扩大**扫描范围（如把 Python 业务目录纳入、把 `.py` 加进 `DEFAULT_EXTS`）。本基线给出的是"安全最小集"的起点而非终点。
