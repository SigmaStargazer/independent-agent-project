# 行为树 (Behavior Tree) 探讨 — EnemyBase FSM 与 Agent ActionSequence

> **状态**：抛砖引玉 / 讨论中
> **提出时间**：2026-07-02（v0.22.1 开发期间）
> **计划推进**：v0.22.1 完成后另立版本（v0.22.X）继续
> **最后更新**：2026-07-02

---

## 0. 文档定位

本文件不是需求，也不是方案，是把 v0.22.1 开发过程中冒出来的一个"是不是该换范式"的疑问先记下来，等本期做完再展开讨论。

两条主线：

1. **EnemyBase 的 FSM 越来越复杂**：从 v0.21.7 的 `Idle / Move / Chase / Stunned`，到 v0.22.1 追加 `Alerted / Investigate / Inspect / Searching`，加上 `mAlertOnly / mPreAlertState / mCurrentSourceDevice / mSourceCooldowns` 等状态外字段，`OnHearAnomaly` 已经出现"六种打断分支 + 三种字段更新组合"的判定表。继续按状态机堆叠，可维护性会成为负担。
2. **Agent 的 ActionSequence 强迫 Agent 描述"每一步"**：当前 DSL 是 `Action + Condition + 下一步 Action` 的线性/条件跳转链条；Agent 本应关心目标、把"怎么做"交给系统，但现在必须把每一步的容错、位置阈值、状态迁移都写进模板。行为树是否能减轻 Agent 的负担、把细节推给树的通用节点？

以下每条只做初步铺陈，正式讨论留到 v0.22.X。

---

## 1. 议题一：EnemyBase 是否应改用行为树

### 1.1 当前 FSM 的痛点（v0.22.1 视角）

- **状态个数快速增长**：v0.21.7 有 4 个状态；v0.22.1 追加 4 个（Alerted / Investigate / Inspect / Searching），Idle 内部还有"回巡逻中 / 抵达等待中"的模式位。
- **状态外字段过多**：`mChaseTarget / mAnomalySource / mLostSightPos / mAlertOnly / mPreAlertState / mCurrentSourceDevice / mSourceCooldowns / mArrivedFromPatrol / mIsReturningToPatrol / mStateTimer / mInspectTurnTimer / mWaitTimer` —— 这些"状态之外的状态"实际决定了 FSM 迁移的走向，读代码时需要横跨多个字段推理。
- **打断规则组合爆炸**：`OnHearAnomaly` 里"当前源识别 / 同源冷却 / 战斗状态 / 自触发 / 异敌 vs 玩家 / 完整调查 vs 仅警觉 / 是否降级 / 是否保留原目标"六七个维度交叉，方案文档写成表格才能表达清楚。
- **优先级隐式**：Chase > 异常事件 > 巡逻 这种优先级不是显式声明的，而是散落在每个状态的 `OnHearAnomaly` 前置判断里。想改优先级要动多处。
- **可组合性差**：想复用"走到某点 → 张望 → 回巡逻"的子流程给 NPC 好奇/巡查/寻物等其他角色，就得把状态类整套复制粘贴。

### 1.2 行为树能带来什么

- **显式优先级**：根节点 Selector 从左到右尝试 `战斗子树 → 异常调查子树 → 巡逻子树`；优先级即树的书写顺序，一目了然。
- **组合子的可复用性**：`MoveToX + FaceX + WaitN + LookAround` 是通用叶子/子树；异常调查、追丢检查、NPC 巡查都能复用。
- **中断即"重跑树"**：新事件到达时不需要"当前状态判断能否打断"，而是让触发条件更高优先级的子树自然抢占；被打断的子树在下次 tick 由 running 变 failure 即可。
- **数据流通过黑板**：`mAnomalySource / mCurrentSourceDevice / mLostSightPos` 等散落字段收敛为角色的 Blackboard，读写路径显式。
- **可视化编辑潜力**：市面上大多数 BT 库都支持可视化编辑（Behavior Designer / NodeCanvas 等），关卡设计师能调整敌人行为而不用碰 C#。

### 1.3 行为树的代价与风险

- **学习成本 + 引入依赖**：项目当前没有 BT 框架；引入 Behavior Designer 等要评估授权；自研最简 BT（约 200~400 行）则要花时间打磨。
- **调试成本**：BT 的执行栈没有 FSM 直观；tick 期间 running 节点复杂时排错要工具支持（tick 可视化面板 / trace 日志）。
- **物理与协程语义**：Unity `FixedUpdate` / `Update` / 协程如何映射到 BT 的 tick 是需要设计的点。
- **过度改造风险**：EnemyBase 只有一个（本期）加一个 SearchingState 就够用；从 FSM 迁 BT 是一次"为未来 5 个敌人类型服务"的投资，如果后续并没有真的做 5 种敌人，投入产出比不划算。
- **打断语义的重新表达**：当前"完整调查中被异敌打断不降级、保留原目标"这类精细规则，在 BT 里要写在 decorator 或黑板策略里，未必更清晰。

### 1.4 若改造，改到什么程度

三档选项（未决策，仅列出）：

| 档位 | 描述 | 影响面 |
|------|------|--------|
| A. 保持 FSM，做局部重构 | 抽出 `InvestigationChain` 组件，把"当前源 / 冷却 / 更新规则"封装成一个可测试单元；FSMState 仍存在 | 小 |
| B. FSM + 行为块 | 保留顶层 FSM（Idle/Move/Chase/Alerted 等），在每个"复杂状态"内部用短行为链（Move→Face→Wait→LookAround）代替 On*Update 手写 | 中 |
| C. 全面行为树 | 引入或自研 BT 框架；EnemyBase 只暴露黑板与叶子节点；顶层 Selector 决定当前该做什么 | 大 |

初步观感：如果只是"再加一种敌人类型"，B 已经够用；如果计划做多种敌人+关卡设计师能调，才考虑 C。

### 1.5 决策所需的先决问题

- 后续 3~6 个月是否会加至少 2~3 种不同行为模式的敌人（守卫 / 追踪者 / 巡视者 / 反应型）？
- 是否需要关卡设计师在编辑器里调敌人行为？
- 现有 FSM 的可维护性痛点是"绝对痛"还是"能忍"？（v0.22.1 之后再评估一次）

## 2. 议题二：行为树是否能优化 Agent 的 ActionSequence

### 2.1 当前 ActionSequence DSL 的痛点

当前设计（见 `Doc/ActionSequence开发流程.md` 与 `action_skill_system/`）：Agent 通过 `plan_action_sequence_cmd` 等工具，写一个含 `ActionStep[]` 的模板，每个 Step 有：

- 具体动作（Move / Wait / Interact / StateChange / …）
- 目标位置或参数（含 `allowed_contact_obj_ids` 之类的"允许接触"清单）
- 跳到下一步的 `Condition` 表达式（DynamicExpresso 求值）

痛点在于**Agent 被迫描述执行细节**：

- 每一步都要显式写"往哪走、走到什么位置停、什么条件切下一步、允许碰哪些物体"。
- 想"等平台开过来"要写 `state == Move + LeftPosition.x < 阈值` 这种细节；写错阈值就撞陷阱。
- 想"抓准时机跳跃"要写多个 Wait/Interact 段配合 `actionTime >= N` 条件。
- 参数化能力有限：v0.21.6 允许 `{占位符}`，但仅字符串；`List[int]` 不能占位（见需求池条目 2）。
- Agent 更容易"生成能编译但不能过关"的模板，因为 DSL 表达的是"执行动作"而不是"意图"。

一句话：**Agent 应该说"我要过陷阱"，而不是"我先 wait 5 秒然后 move 到 x=3.2 然后 …"**。

### 2.2 行为树对 ActionSequence 有什么帮助

BT 在游戏 AI 中的典型用法就是"我给出高层意图（子树名 / 叶子名），系统负责执行细节 + 容错"。若把 ActionSequence 从"线性 DSL"改造成"行为树 DSL"：

- **叶子节点封装通用容错**：`MoveTo(target)` 叶子内部自己处理"如果被平台挡住则等/绕/重试"，Agent 只需说"移动到 target"，不用写 `allowed_contact_obj_ids`、不用写 `actionTime` 条件。
- **Selector 天然表达"降级/备选"**：想"如果开门失败就砸门"直接写 `Selector[OpenDoor, BashDoor]`，比 DSL 中挂 `Condition` 跳步简洁。
- **子树可复用为技能**：常用的"渡陷阱"、"越激光网"作为子树保存到 `ActionSkill` 库，Agent 直接引用子树名 + 参数（`RideMovingPlatform(platform_id=3)`），不用重复描述具体条件与位置。
- **黑板承载环境上下文**：Agent 不用手写"读 SceneObj 的 LeftPosition"，叶子节点自己从黑板取。
- **条件节点显式表达状态判断**：`IsAt(x)`、`ObjectState == Move` 等作为条件节点，比表达式字符串更明确、更好检索。

### 2.3 迁移的可能形态

粗略勾勒（未细化）：

```
Agent 输出：
  Sequence("过第一段陷阱")
    RideMovingPlatform(platform=3, direction=RightToLeft)
    Sequence("再穿激光网")
      WaitFor(LaserOff)
      MoveToPoint("safe_spot_2")

Agent 不再输出：
  Step1: state == "Idle" && LeftPosition.x < 3.2 → next
  Step2: move to 5.5, allowed_contact_obj_ids=[3], actionTime >= 5 → next
  Step3: state == "Idle" → done
```

从 Agent 视角，输出量减少一半以上；从系统视角，需要提供"叶子节点库"（预置常用动作 + 容错），并把 Unity 执行端从"逐帧解释 ActionStep"改成"tick BehaviorTree"。

### 2.4 隐性代价

- **叶子节点的健壮性成为新负担**：叶子内部的容错逻辑（"移动到 x 被挡住怎么办"）不写好，Agent 只是把复杂度从模板转嫁到了叶子实现者。
- **失去精确控制**：Agent 想做一个"卡住 2.3 秒后跳"的极限操作时，行为树的通用叶子未必能表达。得保留 Escape Hatch（允许直接写 Wait/Move 原语）。
- **RAG / 技能库检索的语义变化**：现有 `ActionSkillManager` 是按模板文本做 embedding 检索；BT 化后模板变成结构化子树，需要评估检索能力是否退化。
- **Unity 侧执行端要重写**：`ActionSequenceRuntime` 目前是线性状态机，改成 BT tick 是不小的改造。
- **训练数据不兼容**：现有 default_skills 与训练日志中的模板全是线性 DSL，迁移意味着一次性废弃或做转换器。

### 2.5 温和路径

不必一步到位。可以先在**不改协议**的前提下：

- 在 `ActionSequenceRuntime` 内部把"Move + Wait + 条件"聚合成"Skill 语义叶子"（如 `RideMovingPlatformLeaf`），让 Agent 通过特定占位符/关键字触发，Unity 侧内部展开为具体动作。
- 观察 Agent 是否更倾向使用这类语义叶子；如果确实降低模板出错率，再考虑正式引入 BT。

## 3. 议题一与议题二的联动

两条主线看似独立，其实共享同一个底层问题：**"意图-执行-容错"三者是否要在同一处表达**。

- EnemyBase FSM：把"意图（追、警觉、巡逻）+ 执行（移动、张望）+ 容错（打断、优先级、冷却）"塞在同一份 C# 状态类里，膨胀。
- Agent ActionSequence：把"意图（过陷阱）+ 执行（Move/Wait 步）+ 容错（allowed_contact_obj_ids / 状态判断）"塞在同一份 DSL 里，也膨胀。

如果两边都朝行为树迁移，两个体系可以共享同一套"叶子/子树"抽象（Unity 侧的原语，如 MoveTo / WaitFor / LookAround），Agent 和 EnemyBase 的差别只在树的组装方式和触发源：

- EnemyBase 由 Unity 端事件（视野 / 异常事件 / 打断）驱动黑板 → 决策树 tick。
- Agent 由 Python 侧 LLM 决策 → 生成 BT 结构 → 提交给 Unity 执行。

**共享叶子层**意味着一次基础设施投入可以服务两个业务；反之，如果只改一边，投入回报比会低。

## 4. 推进节奏建议

- **v0.22.1**：不动 FSM 与 ActionSequence 架构；把当前方案跑通、拿到真实痛点数据（新加的 4 个状态、`OnHearAnomaly` 的复杂性在多敌人场景下究竟有多痛）。
- **v0.22.1 完成后**：立一个 `DevDocs/v0.22.X/requirements/` 需求，展开这两个议题；先分别评估、再决定是否合并共享底层。
- **不建议**：跳过 v0.22.1 直接改架构；至少要有一版"复杂但能跑"的 FSM 结果，作为 BT 方案的对照。
