> 立项版本：待定（建议作为独立版本 v0.23.0 或打包里程碑）

## 1. 背景与目标

### 1.1 现状

项目由两部分组成，玩家本机运行：

- **Unity 客户端**（`Src/IndependentAgentProject/`）：游戏本体，负责场景、角色、渲染、输入。
- **Python Agent 服务端**（`Src/PythonServer/`）：Brain，运行 LangGraph Agent、Graphiti/Kuzu 记忆、工具 RPC，监听 `127.0.0.1` 的 TCP 端口。

二者通过 Protobuf + 4 字节小端长度头通信。运行时流程：

1. Python 端 `main.py` 启动，`AgentServerNetMessage.astart()` 用 `port=0` 让 OS 分配空闲端口；
2. 把实际端口写入 `Src/Data/Config/agent_server_port.txt`；
3. Unity 客户端启动后，`AgentService.GetPort()` 从 `Application.dataPath` 上两级目录的 `Data/Config/agent_server_port.txt` 读取端口，连接 `127.0.0.1:port`。

当前所有运行都发生在开发环境：Python 由开发者手动 `uv run python main.py` 启动，Unity 在编辑器里 Play，两边各自看日志。

### 1.2 目标

把整套打包成**单机客户端**，玩家本机运行，**不在服务器上部署任何东西**：

- 玩家拿到一个安装包/压缩包，解压即玩（或安装即玩）。
- **玩家双击 Unity 客户端 exe 即可运行**：客户端进程自动拉起 Python 服务端，无需玩家手动开命令行、无需独立启动器。
- 端口分配与发现机制保持本地化，玩家无感。
- 玩家机器上不需要预装 Python 或 uv。
- **发布包里不含任何开发者 API Key**：玩家在 Title 场景自行配置自己的 LLM/Embedding API Key，配置持久化在玩家本机，运行时注入给 Python。

### 1.3 为打包/运行便利而做的改造（相对当前开发版）

当前开发版的工作流是「开发者先手动起 Python，再 Play Unity，两边各自看日志」，这是开发期合理的状态。但发布版体验不同，以下改造是为了让打包版「玩家点开即用」，同时尽量不破坏开发期工作流：

| 改造点 | 开发现状 | 打包目标 | 是否影响开发期 |
|--------|----------|----------|----------------|
| Python 进程拉起 | 手动 `uv run python main.py` | Unity `BootstrapEntry` 自动 `Process.Start` 拉起 | 否（用 `#if !UNITY_EDITOR` 或运行时开关隔离） |
| API Key 来源 | `.env` 明文（开发者 Key） | Title 场景 UI 配置，存玩家本机，运行时注入给 Python | 开发期可继续用 `.env` |
| Unity 端口查找 | `Application.dataPath` 上两级 | 改为上一级，适配打包后目录 | 用 `#if UNITY_EDITOR` 兼容 |
| Unity 连接失败处理 | 回退 8000，不重试 | 轮询等待 Python 就绪后重连 | 可同时改善开发期 |
| 外部启动器 | 无（依赖手动起 Python） | **不需要**，Unity 自管 Python 生命周期 | - |

### 1.4 非目标

- 不做多玩家联网、不做云存档同步。
- 不把 Agent 推理搬到云端（明确要求本机运行）。
- 不做移动端（Android/iOS）打包——当前 `AgentService.GetPort()` 注释已说明沙盒限制；本期聚焦 Windows PC（必要时兼容 macOS）。
- 不做独立启动器 exe——由 Unity 客户端直接管理 Python 子进程。

## 2. 关键约束与现状梳理

### 2.1 端口文件的路径耦合（最关键）

Unity 端 `AgentService.GetPort()` 当前逻辑（`AgentService.cs:170-196`）：

```csharp
string projectRoot = Directory.GetParent(Application.dataPath).Parent?.FullName;
string filePath = Path.Combine(projectRoot, "Data", "Config", "agent_server_port.txt");
```

- **编辑器下**：`Application.dataPath = Src/IndependentAgentProject/Assets`，上两级是 `Src/IndependentAgentProject`，再拼 `Data/Config/...` 指向 `Src/IndependentAgentProject/Data/Config/...`（仓库端口文件实际在 `Src/Data/Config/`，靠开发期手动同步）。
- **打包后（Standalone Windows）**：`Application.dataPath = <游戏根>/<产品名>_Data`，`Parent` 是游戏根，再 `Parent` 是游戏根的上级。端口文件会被定位到**游戏根上一级的 Data/Config**，与打包目录结构不符，触发 `FileNotFoundException` 回退到 `8000`。

**结论**：打包必须同步改造 Unity 端口查找路径，使其指向打包后确定可写的位置（见 §3.3）。

### 2.2 Python 运行时与依赖

- `pyproject.toml`：`requires-python >= 3.11`，`uv.lock` 实际锁定 `python_full_version >= 3.12`。
- 重依赖：`kuzu>=0.11.3`（含 C 原生扩展，平台相关 wheel）、`langchain-openai`、`langgraph`、`neo4j`（驱动，非服务端）、`graphiti_core`（仓库内本地包）。
- 启动方式：`uv run python main.py`（依赖 uv 解析 `pyproject.toml` + 虚拟环境）。
- 玩家机器不能假设有 Python/uv。

### 2.3 本地数据与可写目录

Python 端运行时写入：

| 路径 | 内容 | 必须可写 |
|------|------|----------|
| `Src/PythonServer/db/graphiti.kuzu` + `.wal` | Kuzu 图库主库 | 是 |
| `Src/PythonServer/db/backups/slot_n/` | 记忆备份槽 | 是 |
| `Src/PythonServer/db/default_skills/exports/` | 技能导出 YAML | 是（`AgentExportSkillsRequest` 会写） |
| `Src/PythonServer/logs/console/*.log` | 控制台日志镜像 | 是 |
| `Src/PythonServer/logs/prompts/` | Prompt 保存（开发模式） | 是（`PROMPT_SAVE_ENABLED=true` 时） |
| `Src/Data/Config/agent_server_port.txt` | 端口文件 | 是 |

`DBConnectionService` 用相对路径 `DB_ROOT="db"`，依赖**进程工作目录**。打包后若把 Python 资源放进只读区（如 `Program Files`），Kuzu 会因无法写文件而启动失败。

### 2.4 云端 API 依赖（玩家自备 Key 策略）

`.env` 中配置了多个云端 LLM/Embedding/Reranker：

- Agent 对话：`AGENT_API_BASE` / `AGENT_API_KEY` / `AGENT_MODEL`
- 记忆抽取：`MEMORY_API_BASE` / `MEMORY_API_KEY` / `MEMORY_MODEL`
- Embedding：`EMBEDDING_API_BASE` / `EMBEDDING_API_KEY` / `EMBEDDING_MODEL`
- Reranker：`RERANKER_API_BASE` / `RERANKER_API_KEY` / `RERANKER_MODEL`
- Tavily 联网搜索（可选）

**已定策略：玩家自备 Key**。发布包不含任何开发者 Key，玩家在 Title 场景填写自己的 Key，由 Unity 持久化到玩家本机，启动 Python 子进程时注入。详见 §4、§6。

### 2.5 协议与生成代码

`Tools/message.proto` 是权威源；`Src/PythonServer/network/message_pb2.py` 与 Unity 的 `message.cs` 都是生成物。打包时 Python 端只需 `message_pb2.py`（已生成），不需要 protoc 工具链。

### 2.6 Python 配置读取机制

Python 端多处用 `from dotenv import load_dotenv; load_dotenv()` + `os.getenv(...)`（`agent_interuptible.py:45-46`、`memory_manager.py:27-28`、`embedder_service.py:19-27`）。改造后（§4.3、§4.6）Python 无 Key 启动，延后到收到 init 信号时读 `api_config.json` 再初始化；开发期读不到该文件时 fallback 到 `.env`。

## 3. 推荐方案：Unity 托管 Python + 内嵌运行时

### 3.1 打包后目录结构

推荐「单根目录 + 子目录」结构，整个游戏根目录可写，避免装到 `Program Files`：

```
<游戏名>/                          ← 玩家解压/安装根目录，可写
├── <产品名>.exe                   ← Unity 构建产物（Windows），玩家双击入口
├── <产品名>_Data/                 ← Unity 数据目录（只读，构建产物）
│   └── ...
├── PythonServer/                  ← Python 运行时 + 业务代码
│   ├── python/                    ← 内嵌 Python 解释器（python-build-standalone 3.12）
│   ├── runtime/                   ← 依赖包（pip install --target 的 site-packages）
│   ├── main.pyc                   ← 业务代码（v0.23.6 后为 .pyc，见下方说明）
│   ├── agent_framwork/            ← 内为 .pyc
│   ├── memory_system/             ← 内为 .pyc
│   ├── graphiti_core/             ← 内为 .pyc
│   ├── network/                   ← 内为 .pyc
│   ├── tools/                     ← 内为 .pyc
│   ├── db/                        ← Kuzu 库 + 备份 + 默认技能（运行时生成/写入）
│   └── logs/                      ← 运行日志（运行时生成）
├── Data/
│   └── Config/
│       ├── agent_server_port.txt  ← 端口文件（运行时写入） 
│       └── api_config.json        ← 模型api配置（Unity的Title Scene写入，从Title Scene进入游戏场景时被Python端加载）
└── （无独立启动器）
```

> **关于 `.py` vs `.pyc`**：上面目录里业务代码标为 `.pyc` 是**v0.23.6 完成后的最终形态**。在 v0.23.1-v0.23.5 阶段，业务代码仍是 `.py` 明文（便于调试验证）。v0.23.6 通过 `python -m compileall` 预编译后删除 `.py`，只分发 `.pyc`。所以「最终客户端程序里不包括 `.py`」是 v0.23.6 之后才成立，之前的版本仍含 `.py` 用于逐步验证功能正确性。

**设计要点**：

1. **整个游戏根目录可写**：装到玩家选择的目录或 `%LOCALAPPDATA%/<游戏名>/`。Kuzu、logs、db 直接相对路径写入，`DBConnectionService` 零改动。
2. **端口文件放游戏根的 `Data/Config/`**：与 §3.3 Unity 查找路径对齐。
3. **Python 解释器内嵌**：`python-build-standalone` 随包分发，玩家无需装 Python。
4. **依赖预装**：打包时 `pip install --target=PythonServer/runtime/`，运行时 `PYTHONPATH` 指向它，不依赖 uv/虚拟环境。
5. **无独立启动器**：由 Unity 客户端进程直接 `Process.Start` 拉起 Python，并负责退出时清理（见 §3.4）。

### 3.2 Python 运行时打包方式

| 方式 | 说明 | 体积 | 复杂度 | 推荐 |
|------|------|------|--------|------|
| **内嵌 python-build-standalone + 预装依赖** | 下 `python-3.12` 放 `PythonServer/python/`，`pip install -t runtime/` 装依赖 | 中（~300-500MB） | 中 | 推荐 |
| **PyInstaller 打成单 exe** | 把 main.py + 依赖全打进一个 exe | 大（~600MB+） | 高（kuzu C 扩展、graphiti 本地包需 hooks） | 不推荐 |
| **Nuitka 编译** | 编译为原生代码 | 中 | 高 | 不推荐 |

推荐内嵌解释器 + 预装依赖：

- 用 `python-build-standalone`（astral 出品，uv 也用它）提供 `python.exe`。
- `pip install --target=PythonServer/runtime/ -r requirements.txt` 装依赖。
- 启动时 `PYTHONPATH=PythonServer/runtime;PythonServer` 运行 `main.py`。
- **kuzu 平台 wheel**：打包机必须是 Windows x64，`pip install kuzu` 拿到对应 wheel，复制到 `runtime/` 即可。


**python-build-standalone 方案详解（为何选它）**

`python-build-standalone` 是 astral（uv 的开发商）维护的项目，提供预编译、可重定位的 CPython 发行版。选它而非其他方案的理由：

| 维度 | python-build-standalone（选） | Python 官方 embeddable zip | PyInstaller | Nuitka |
|------|------------------------------|----------------------------|-------------|--------|
| **形态** | 完整 Python 安装目录（含 pip、stdlib、可重定位） | 极简 zip，**无 pip**，需手动配 | 单 exe/目录，冻结式 | 编译为原生代码 |
| **pip 可用** | ✅ 直接 `pip install` | ❌ 需手动 bootstrap | N/A（打包时解析） | N/A |
| **依赖管理** | `pip install --target` 装到任意目录，清晰可控 | 手动拷 wheel，易错 | 打包时自动分析 import，隐式 | 同 PyInstaller |
| **C 扩展（kuzu）** | ✅ 正常 pip 装 wheel 即可 | 需手动处理路径 | 需写 hooks，易踩坑 | 编译易出错 |
| **本地包（graphiti_core）** | ✅ 靠 PYTHONPATH 引入，简单 | 同左 | 需配置 hooks | 需配置 |
| **跨平台** | ✅ 提供 Win/macOS/Linux 多平台构建 | ❌ 仅 Windows | ✅ 但非交叉编译 | ✅ 但非交叉编译 |
| **调试** | ✅ 目录结构透明，可单独跑 python.exe | 透明 | 黑盒，出错难查 | 黑盒 |
| **体积** | 中（解释器 ~30MB + 依赖） | 小（但需补 pip） | 大（冻结冗余） | 中 |
| **与 uv 一致** | ✅ uv 本身就用它 | - | - | - |

**核心优势**：它本质就是一个「可拷贝即用」的完整 Python 目录，`pip install --target` 把依赖装到指定位置，运行时靠 `PYTHONPATH` 找到。整个过程**透明、可控、可调试**--出了问题能直接进目录看文件、单独跑 `python.exe` 验证。相比之下 PyInstaller/Nuitka 是「冻结/编译」黑盒，对 kuzu 这类含 C 原生扩展的库需要写 hooks、易踩坑且难排查。官方 embeddable zip 又太精简（无 pip），依赖管理麻烦。

**为 macOS 预留**：python-build-standalone 同样提供 macOS（arm64 + x86_64）构建，后续 macOS 打包时只需下载对应平台构建、装对应平台 wheel，脚本结构可复用。
### 3.3 端口发现机制改造（Unity 侧）

必须改 `AgentService.GetPort()`，使其在打包后能正确找到端口文件。

**方案 A（推荐）：统一相对 `Application.dataPath` 上级**

打包后 `Application.dataPath = <游戏根>/<产品名>_Data`，`Parent` 即游戏根。把端口查找改为：

```csharp
#if UNITY_EDITOR
    // 编辑器下保持原逻辑（指向 Src/Data/Config）
    string projectRoot = Directory.GetParent(Application.dataPath).Parent?.FullName;
#else
    // 打包后指向游戏根
    string projectRoot = Directory.GetParent(Application.dataPath)?.FullName;
#endif
    string filePath = Path.Combine(projectRoot, "Data", "Config", "agent_server_port.txt");
```

即打包分支去掉当前的 `.Parent?.Parent`，改为 `.Parent`，端口文件落在 `<游戏根>/Data/Config/`，与 §3.1 结构一致。

**方案 B（备选）：用 `Application.persistentDataPath`**

端口文件写到 OS 标准可写区（`%LOCALAPPDATA%/<公司名>/<产品名>/`），Unity 与 Python 都改读写该路径。改动面更大，且与「游戏根目录一体化」目标偏离，不推荐。

### 3.4 Unity 托管 Python 进程生命周期

这是「点开 Unity 即用」的核心。三个时间点必须理清（见 §4.3）：

1. **启动 Python 端**：在 `BootstrapEntry` 里，**无 Key 启动**（只监听端口）。
2. **配置 API Key**：在 Title 场景里，玩家填写。
3. **真正用上 API Key**：在 Title 点「开始游戏」/「继续游戏」后，Unity 发 init 信号，Python 读 `api_config.json` 再初始化。

故 Python 进程分两段管理：启动在 `BootstrapEntry`，init 信号在 Title 点开始游戏时。完整时序：

1. **BootstrapEntry 启动 Python 子进程（无 Key）**：Python 经 §4.6 改造后无 Key 也能启动并监听端口，不读任何 Key：

```csharp
// 伪代码，实际封装到 PythonProcessLauncher
var psi = new ProcessStartInfo
{
    FileName = Path.Combine(gameRoot, "PythonServer", "python", "python.exe"),
    Arguments = "main.py",
    WorkingDirectory = Path.Combine(gameRoot, "PythonServer"), // 保证 db 相对路径生效
    UseShellExecute = false,
    CreateNoWindow = true,
};
// 无需注入 Key：Python 无 Key 启动，init 信号时再读 api_config.json（§4.3）
pythonProcess = Process.Start(psi);
```

2. **等待 Python 就绪**：轮询端口文件存在且非 `0`，超时报错（Python 启动失败提示）。同时改 `AgentService.ConnectToServer()` 失败后重试，而非直接回退 8000。就绪后进 Title 场景。
3. **Title 场景配 Key**：玩家填写 API Key（首次）或读已有配置，存 `Data/Config/api_config.json`（加密，§4.2）。`IsComplete()` 为 false 则弹配置面板，不让进游戏。
4. **点「开始游戏」发 init 信号触发 Python 初始化**：Unity 连上后、进场景前，发 `InitRequest`（或复用 `SceneStartRequest`）。Python 收到后先读 `Data/Config/api_config.json`（§4.2），用读到的 Key 跑 `MemoryManager.initialize()` 构造 LLM/Embedder（§4.6）。**这一步是 Python 真正「需要 Key」的时刻，此时 Key 从文件读入**。
5. **退出时清理**：`Application.OnApplicationQuit` 或 `BootstrapEntry.OnApplicationQuit` 中 `pythonProcess.Kill()`，避免残留进程。

**开发期隔离**：Bootstrap 的自动拉起逻辑用 `#if !UNITY_EDITOR` 包裹，编辑器下仍由开发者手动起 Python。Python 端可加 `--auto-init` 参数供开发期自动跑 initialize（见 v0.23.3）。

### 3.5 启动器选型结论

不再需要独立启动器（§1.4 非目标）。所有「Bootstrap 起 Python、等端口、进 Title、配 Key、点开始游戏发 init 信号、进场景、退出清理」逻辑都收进 Unity 客户端，由 `BootstrapEntry` + `Title 场景控制器` + `PythonProcessLauncher` + `AgentService` 协作完成。Python 启动在 BootstrapEntry（无 Key），init 信号在 Title 点开始游戏时，见 §4.3 时序。

### 3.6 Python 端源码保护（是否打包/混淆）

**问题**：若 Python 以 `.py` 源码形式随包分发（§3.1 结构），`main.py`、`agent_framwork/`、`memory_system/` 等业务代码对玩家完全可见、可改。存在两个风险：

1. **源码暴露**：业务逻辑、prompt 构造、记忆系统实现被直接读取。
2. **篡改风险**：恶意程序或玩家可修改 `.py`，注入恶意逻辑、绕过校验、或修改与 Unity 的通信协议。

**可选保护方式**：

| 方式 | 保护程度 | 复杂度 | 体积影响 | 备注 |
|------|----------|--------|----------|------|
| **A. 明文 `.py` 分发** | 无 | 最低 | 无 | 现状；玩家可直接读改 |
| **B. 预编译 `.pyc` 分发** | 低（可反编译） | 低 | 略减 | `python -m compileall`；挡不住有意者，但避免误改 |
| **C. Cython 编译为 `.pyd`（C 扩展）** | 中高（难反编译） | 高 | 增 | 需为每个模块编 C；kuzu/graphiti 等含原生扩展的需单独处理 |
| **D. Nuitka 编译为原生 exe/dll** | 中高 | 高 | 增 | 整体编译；调试难；kuzu C 扩展易踩坑 |
| **E. PyArmor 加密 `.py`** | 中（运行时解密） | 中 | 增 | 商业工具，需 license；有性能开销 |
| **F. 关键逻辑移入 Unity（C#）侧** | 高 | 高 | 减 Python | 架构级重构，违背 Brain/Environment 分层 |

**推荐分阶段**：

- **MVP / 内部测试**：用 **B（预编译 `.pyc`）**。零额外工具成本，`python -m compileall PythonServer` 后只分发 `.pyc`（删除 `.py`）。能挡住误改和随手窥探，对有意逆向效果有限。
- **正式发布**：评估 **C（Cython）** 或 **E（PyArmor）**，按需保护核心模块（`agent_interuptible.py`、`memory_manager.py`、`base_tools.py`）。依赖（langchain/kuzu 等）本身已是编译产物，无需额外处理。

**完整性校验（不论哪种方式都建议加）**：Python 启动时可选地校验自身关键文件哈希（与打包时记录的基准比对），被篡改则拒绝启动并提示。这能缓解恶意篡改风险，但对完全控制机器的攻击者无法根治。

**注意**：源码保护与「玩家自备 Key」是正交的--Key 不在 Python 端，篡改 Python 代码拿不到 Key。保护的重点是业务逻辑与协议完整性。

### 3.7 端口策略：随机端口 vs 固定端口

**现状**：`AgentServerNetMessage.astart()`（`servers.py:68-83`）用 `port=0` 让 OS 分配空闲端口，再写入端口文件，Unity 读取。这是为了避免端口被占用。

**两种策略对比**：

| 维度 | 随机端口（现状） | 固定端口 |
|------|------------------|----------|
| 端口冲突 | 几乎不可能 | 可能被其他程序占用；需选不常用端口（如 49152-65535 段） |
| 多开 | 天然支持（两玩家可同时开） | 同机多开冲突 |
| 实现复杂度 | 需端口文件发现机制（当前已有） | 简单，写死即可 |
| Unity 连接 | 必须读端口文件 | 可写死，但 Python 没起来时 Unity 会连失败需重试 |
| 安全性 | 略好（端口不固定，难猜） | 略差（固定端口可被外部扫到） |
| 调试 | 端口每次变，日志对照稍麻烦 | 固定，好对照 |

**关键考量**：

1. **监听地址已是 `127.0.0.1`**（`servers.py:72`），不暴露到外网，安全性差异在单机场景可忽略。
2. **同机多开**：单机游戏一般不要求多开，但随机端口天然兼容，无坏处。
3. **端口文件机制已存在且可用**，随机端口不增加额外复杂度（Unity 已实现读端口文件）。

**推荐：保留随机端口**。理由：

- 端口文件发现机制（Python 写 / Unity 读）已经实现且 §3.3 改造后打包可用，随机端口「零额外成本」。
- 彻底避免「固定端口被占用导致启动失败」的玩家支持负担--玩家机器环境不可控，固定端口被占是常见问题（杀毒软件、其他游戏、开发工具常占用端口）。
- 固定端口在单机 `127.0.0.1` 场景带来的好处（简单）已被端口文件机制抹平。

唯一需注意的是 §3.3 Unity 端口路径改造与 §3.4 等待端口就绪逻辑，这两点对随机端口是必须的（固定端口可省等待，但仍建议保留以应对 Python 慢启动）。

### 4.3 API Key 注入与时序（已定）

**核心问题：三件事的时序**

整个流程涉及三个时间点，必须理清：

1. **启动 Python 端**：在 `BootstrapEntry` 里，**无 Key 启动**（只监听端口）。
2. **配置 API Key**：在 Title 场景里，玩家填写（首次）或读已有配置。
3. **真正用上 API Key**：在 Title 场景点击「开始游戏」/「继续游戏」以后。

经核查 Python 侧代码，当前阻碍这个时序的根因：

- `agent_interuptible.py:125-131` 在**模块 import 时** `os.getenv("AGENT_API_*")` 并构造 `ChatOpenAI` 实例 `model`；`llm_with_tools = model.bind_tools(tools)`（181 行）也是模块级执行。
- `memory_manager.py:30-32` + `__init__:51-63` 在 import / 实例化时构造 `LLMConfig` 与压缩模型，Key 固化为字段。
- `embedder_service.py:62-86` 在 `initialize()` 时构造 embedder/reranker，同样固化 Key。
- 但**三处构造均不发网络请求**，真正报错发生在首次调用 LLM/Embedder 时（401）。

**已定方向：Python 无 Key 启动 + 延后 initialize + 读 api_config.json**

让 Python 能在无 Key 状态下启动并监听端口；玩家配好 Key 后，Unity 发 init 信号，Python 读 `api_config.json` 再跑 initialize。具体改造见 §4.6。改造后流程：

```
双击 exe
  -> BootstrapEntry：拉起 Python（无 Key，只监听端口）
  -> 进 Title 场景
  -> 玩家填 Key（首次）或读已有配置，存 api_config.json（加密，§4.2）
  -> 玩家点「开始游戏」/「继续游戏」
    -> Unity 发 init 信号（或复用 SceneStartRequest）
    -> Python 收到信号，读 api_config.json，用读到的 Key 跑 MemoryManager.initialize() + 构造 Agent LLM
    -> 进场景
```

**配置流向**：Unity（玩家填）-> 写 `Data/Config/api_config.json`（加密，§4.2）-> Python 收到 init 信号后读该文件 -> 构造 LLM/Embedder。

要点：

- **发布包无 `.env`、无开发者 Key**（打包时排除 `Src/PythonServer/.env`）。
- 玩家 Key 只存在玩家本机的 `api_config.json`（加密存储，§4.2），Python 延后初始化时读取。
- 开发期 Python 仍可读 `.env`（读不到 api_config.json 或字段为空时 fallback 到 `.env`，兼容现有开发工作流）。
- 配置变更（玩家改 Key）：Title 改完存文件，点开始游戏时 Python 重新读文件初始化。**改 Key 无需重启 Python/游戏**：v0.23.0b 生命周期架构下，回 Title 即 `CloseRequest` → Python `leave_game()` 关闭全部系统（零系统），再进游戏 `InitRequest` → `enter_game()` 用 `force=True` 读最新 `api_config.json` 全新初始化，新 Key 即生效。
- 不经环境变量注入：Python 启动在 Bootstrap（早于玩家配 Key），环境变量无法在进程启动后追加，故改用「Python 主动读文件」方式。

#### `.env` 职责划分（打包版）

当前 `.env` 含三类内容，打包版处理方式不同：

| 类别 | 字段 | 打包版处理 |
|------|------|-----------|
| **A. API Key 及供应商配置** | `LLM_PROVIDER`、`ANTHROPIC_API_KEY`、`AGENT_API_*`、`MEMORY_API_*`、`EMBEDDING_API_*`、`RERANKER_API_*`、`TAVILY_API_KEY` | **不进 `.env`、不进打包**。玩家在 Title 配置，存 `api_config.json`，Python init handler 读后塞 `os.environ`（§4.3） |
| **B. 运行时调参项** | `MEMORY_QUEUE_SIZE`、`MAX_BACKUP_SLOTS`、`PROMPT_SAVE_*`、`AGENT_MAX_CONTEXT_TOKENS`、`CONTEXT_RESERVE_RATIO`、`OUTPUT_RESERVE_TOKENS`、`CONSOLE_LOG_ENABLED`、`AGENT_LLM_*`、`MEMORY_COMPRESS_*` | **不进 `.env`**。代码里 `os.getenv(..., 默认值)` 全有兜底，不带 `.env` 也能跑。个别需覆盖的由 Unity 启动时注入环境变量（见下） |
| **C. 注释掉的旧配置** | 第 8-16 行注释掉的 Kimi/GLM 旧 Key | **不进打包**；开发期也建议清理（含历史 Key 残留） |

**结论：打包版不带 `.env`，也不需要 `.env.example` 和运行时复制机制。**

理由：
1. B 类参数代码已有默认值兜底，没 `.env` 也能跑。
2. 需强制覆盖默认值的仅两项，由 Unity 启动 Python 时通过 `ProcessStartInfo.EnvironmentVariables` 注入，比维护 `.env` 文件更干净：
   - `PROMPT_SAVE_ENABLED=false`（代码默认已是 `false`，但当前 `.env` 写 `true`，打包版必须确保 `false`，避免写 prompt 到玩家磁盘）
   - `CONSOLE_LOG_ENABLED=false`（代码默认 `true`，打包版建议 `false` 减少写盘；若希望玩家报错时能提供日志，可保留 `true`）
3. 发布包里既无 `.env` 也无 `.env.example`，玩家本机也不生成 `.env`，配置全走 `api_config.json`，职责清晰。

> 注：Unity 注入这两个环境变量与「不经环境变量注入 Key」不矛盾--这两个是行为开关，不是 Key，且 Python 启动时（Bootstrap）就确定，不需要等玩家配置。

### 4.6 Python 侧延迟初始化改造（支撑 §4.3 时序）

为让 Python 能无 Key 启动、延后到收到 Unity 信号后再初始化，需改造以下点。**此改造属 Python 侧架构改动，待方案确认后再执行，遵循 §开发纪律**。

| 文件 | 改动 | 说明 |
|------|------|------|
| `main.py` `main()` | 移除全局 `await MemoryManager().initialize()`（第 312 行） | `main()` 只起 `server.astart()` 监听端口，不跑记忆/LLM 初始化。`initialize()` 延后到收到 Unity 的初始化信号 |
| `main.py` | 新增 `InitRequest`（或复用 `SceneStartRequest`）handler，触发 `MemoryManager().initialize()` | Unity 连上后、进场景前发此信号；Python 收到后读 `api_config.json` 获取 Key，再跑 initialize |
| `agent_interuptible.py:125-181` | `model` / `llm_with_tools` 从模块级变量改为延迟构造 | 当前 import 时就 `os.getenv`+构造，Key 固化为 None。改为首次用时或 init 信号到达后再构造（工厂函数或全局延迟初始化）。`tools` 列表本身不依赖 Key，可保持模块级 |
| `memory_manager.py:30-32,51-63` | `LLMConfig` / 压缩模型构造延后 | 当前 `__init__` 时就固化 Key。改为 `initialize()` 内构造（此时 Key 已在） |
| `embedder_service.py` | 无需改动 | `initialize()` 本就是延后调用，只需保证调用时机在 Key 注入后 |

**风险与注意**：

1. `AgentManager.acreate_agent` / `aload_agent_all` 会构造 `Agent` 实例，`Agent` 绑定 `llm_with_tools`。若 `llm_with_tools` 延迟构造，需保证 Agent 创建时已初始化完成，否则 `chatbot` 节点取不到。用「init 信号到达后才允许创建 Agent」的顺序保证。
2. 模块级 `load_dotenv()` 保留无妨（它只是把 `.env` 读进环境变量，不构造对象）。真正要改的是「模块级构造对象」那几处。init handler 读 `api_config.json` 后，把读到的值写进 `os.environ`，这样后续 `os.getenv` 能读到（复用现有读取逻辑，无需改 `os.getenv` 调用点）。
3. 开发期影响：编辑器下 Unity 不自动起 Python，开发者手动起 Python 后仍可手动触发 initialize（或保留一个 `--auto-init` 命令行参数供开发期用）。

4. **7z 压缩**：最终包用 7z 而非 zip，体积可再降 30-40%。
5. **日志降级**：`CONSOLE_LOG_ENABLED=false`（已有支持），`PROMPT_SAVE_ENABLED=false`。

### 7.3 启动性能

- Python 服务端初始化（Kuzu 建库 + FTS + Graphiti schema）约数秒，Unity `BootstrapEntry` 需等端口就绪，玩家会看到短暂加载。建议加进度提示。

- **开发期不受影响**：v0.23.0 端口路径用 `#if UNITY_EDITOR` 隔离；v0.23.2 自启 Python 用 `#if !UNITY_EDITOR` 隔离；v0.23.3 延迟初始化在编辑器下可用 `--auto-init` 兼容；v0.23.4 API 配置在编辑器下可继续用 `.env`。开发工作流在每个版本都保持可用。
- **最关键的 API Key 安全问题在 v0.23.4 解决**，v0.23.5 才产出可分发包，避免在 Key 安全未解决时就产出可泄露的包。
- **源码保护放最后**（v0.23.6）：前序版本优先验证功能正确性，源码保护是发布前加固，不影响功能。
- **已发现的隐患**（v0.23.0 顺带处理）：`ClientBase.DoConnect()` 当前用 `BeginConnect` + `WaitOne(10000)` 阻塞主线程，3 次重试会卡顿 30 秒。v0.23.0 改连接重试时需注意避免主线程长时间阻塞（改用协程/UniTask 异步重试，而非复用现有的同步 `DoConnect`）。

## 11. 全部完成后的打包操作流程

v0.23.0-v0.23.6 全部完成后，每次发布新版本的打包操作流程如下。假设打包机为 Windows x64，已预装 Unity 2021.3.8f1c1 和 Python 3.12。

### 11.1 一次性准备（仅首次）

1. **确认打包机环境**：Unity 2021.3.8f1c1、Python 3.12（用于跑 pip，不进产物）、可选 uv。
2. **轮换/禁用旧开发者 Key**：在各供应商后台（火山、阿里云、Tavily）禁用 `.env` 里的旧 Key，确保发布包即使误带也不可用。
3. **首次运行** `Tools/build_python_runtime.cmd`：下载 python-build-standalone 并缓存，装依赖到 `runtime/`。后续打包可复用缓存。

### 11.2 每次发布打包（日常流程）

```
① 拉最新代码到打包机
        ↓
② 检查 Src/PythonServer/.env 不含要发布的 Key（应已轮换）
        ↓
③ 执行 Tools/build_package.cmd
        ↓
④ 脚本自动完成：
     a. Unity -batchmode -buildWindows64Player 产出 exe + _Data
     b. 复用/刷新 PythonServer/python/ + runtime/
     c. 拷贝业务代码
     d. python -m compileall 预编译，删除 .py，只留 .pyc（v0.23.6）
     e. 排除 .env / 开发 db / logs / 测试文件
     f. 生成 Data/Config/agent_server_port.txt 占位（内容 0）
     g. 打 7z/zip
        ↓
⑤ 产出 build/MyGame.zip
        ↓
⑥ 在干净机器（无 Python/uv/Unity）解压验证
        ↓
⑦ 发布：打 tag + 传 GitHub Releases 附件（见 §11.6）
```

**重新打包注意事项（覆盖式 Build，无需先删 Build/）**：

- Unity Build 到同一目录（如 `build/`）时**会自动覆盖**它自己生成的产物（`<产品名>.exe`、`<产品名>_Data/` 等），**无需手动删除整个 `build/`**。
- Unity 只清它管理的文件，**不会删 `Data/Config/` 下手动放置的内容**（如联调时放的 `agent_server_port.txt`、Title 生成的 `api_config.json`）——重新 Build 后这些通常仍在。
- 例外：若你**改变了产品名**、把 Build 输出到**别的位置**、或怀疑有陈旧 DLL/meta 残留，可手动清理，但注意**不要误删 `Data/Config/agent_server_port.txt`**（若删了整目录，重新 Build 后需重新放端口文件）。
- Build 成功后若运行异常，先核对 Console/日志中 `GetPort filePath:` 打印的路径是否为 `<构建输出根>/Data/Config/agent_server_port.txt`（打包分支，§3.3 方案 A），可快速判断端口文件是否放对层。

### 11.3 干净机器验证清单

在另一台没装开发环境的 Windows 机器上解压 `MyGame.zip`，按以下步骤验证：

1. **双击 `<产品名>.exe`**：应自动拉起 Python（任务管理器可见 python.exe），短暂加载后进入 Title。
2. **首次配置 API**：Title 场景弹出 API 配置面板，填入自己的 Key，保存。
3. **新游戏/继续游戏**：能正常进场景，Agent 能推理、能记忆检索（说明 Key 注入生效）。
4. **检查包内容**：解压目录内无 `.env`、无 `.py`（只有 `.pyc`）、无 `graphiti.kuzu`、无 `logs/`。
5. **退出清理**：退出游戏后任务管理器无残留 `python.exe`。
6. **改 Key 生效**：在 Title 改 Key 后，点开始/继续游戏进入场景（回 Title 时已自动关闭系统，再进游戏全新初始化），新 Key 生效，无需重启游戏。

### 11.4 玩家侧体验流程（最终用户）

1. 下载 `MyGame.zip`，解压到任意可写目录（不要解压到 `Program Files`）。
2. 双击 `<产品名>.exe`。
3. 首次启动：Title 场景提示配置 API Key（玩家需自备 GLM/火山/阿里云等 Key）。
4. 填完 Key 后点「新游戏」或「继续游戏」，自动起 Python、连接、进场景。
5. 后续启动：自动读取已保存的 Key，直接进游戏（除非玩家主动改 Key）。
6. 退出游戏时 Python 进程自动清理。

### 11.5 常见问题排查

| 现象 | 可能原因 | 排查 |
|------|----------|------|
| 双击 exe 后卡住不进 Title | Python 启动失败 | 看 `PythonServer/logs/console/` 最新日志 |
| 进游戏后 Agent 不响应 | API Key 无效或网络不通 | Title 重新配 Key；检查 `api_config.json` |
| 连接超时报错 | 端口文件未生成 | 确认 Python 进程是否在运行；看 Python 日志是否建库失败 |
| `kuzu` 加载失败 | Python 版本不匹配 | 确认打包机与运行时 Python 版本一致 |
| 解压到 Program Files 后报错 | 目录不可写 | 提示玩家解压到其他目录 |

### 11.6 发布到 GitHub Releases（分发方案）

打包的最终产物是 `build/MyGame.zip`（§11.2 步骤 ⑤）。**发布时把 zip 作为 GitHub Releases 的附件（Release Asset）分发，不放进 git 仓库源码树**。原因：

1. **zip 不是源码**：git 仓库托管的是「能构建出 zip 的源代码」；zip 是构建产物，可随时用 `build_package.cmd` 重新生成，不应进 git 历史。
2. **体积**：打包 zip 约 500MB~1GB（含 Unity `_Data`、内嵌 Python、依赖），commit 进仓库会撑爆仓库、拖慢每个克隆/拉取。`.gitignore` 已用 `**/[Bb]uild/` 忽略 `build/` 目录。
3. **Release 附件独立于 git 源码树**：附件下载由 GitHub Releases 提供，不影响仓库的 `clone`/`pull` 体验；源码与发布物职责分离。
4. **含运行时数据**：zip 内含玩家 `api_config.json`（Key）等运行时数据，不能入库；挂 Release 附件由发布者手动控制。

**为什么不用「仓库页面右上角 Download ZIP」**：那个 zip 是 GitHub 在点击时实时把源码打包生成的，不含 Release 附件、也不含 `.gitignore` 忽略的内容，且没有版本号/变更说明，不适合作为正式发布物。正式发布用 Releases 附件。

**发布步骤（每发布一个新版本执行一次）**：

```
前提：已完成 §11.2 打包（产出 build/MyGame.zip）并通过 §11.3 干净机器验证
        ↓
① 打 git tag：git tag vX.Y.Z（与版本号对应，如 v0.23.5）；可选先 git push origin <branch>
        ↓
② 推 tag：git push origin vX.Y.Z
        ↓
③ 在 GitHub 仓库页面 → Releases → 新建 Release（Draft a new release）
        ↓
④ 填写：
     - Tag：选择刚推的 vX.Y.Z（或输入新 tag 自动创建）
     - Title：如「v0.23.5 - 可玩 Demo」
     - Notes：本版变更说明（引用对应 DevDocs/vX.Y/ 的 PRD 主题、修复、已知问题）
        ↓
⑤ 上传附件：把 build/MyGame.zip 拖进「Attach binaries」→ 等待上传完成
        ↓
⑥ 点击「Publish release」
        ↓
⑦ 玩家即可在 Release 页面下载 zip
```

**发布清单（发布前逐项确认）**：

- [ ] `build/MyGame.zip` 已通过 §11.3 干净机器验证（能起 Python、能配置 Key、能进游戏）。
- [ ] 包内无 `.env`、无 `.py`（只有 `.pyc`）、无开发者 Key（`Src/PythonServer/.env` 的 Key 已轮换/禁用）。
- [ ] tag 版本号与 `DevDocs/vX.Y/` 版本目录一致。
- [ ] Release Notes 写清本版内容与已知问题。
- [ ] 附件上传完成（体积大时等待进度条走完，避免「发布后附件缺失」）。

**发布后回填**：可在对应 `DevDocs/vX.Y/solution.md` 的「实现记录」补一行「已发布 vX.Y.Z，zip 挂 GitHub Releases 附件」。

> 说明：以上流程对 macOS 发布同样适用（§12 macOS 产物 `.dmg`/`.zip` 也走 GitHub Releases 附件分发）。

## 12. macOS 支持评估

### 12.1 当前方案是否只能在 Windows 上运行？

**是的，当前 v0.23 规划的产物默认只针对 Windows x64**。原因不在架构，而在几个 Windows 特定的打包/运行细节：

1. **内嵌 Python 解释器**：v0.23.1 用的是 python-build-standalone 的 Windows 版（`python.exe`）。
2. **打包脚本**：v0.23.5 的 `build_package.cmd` 是批处理，调用 `Unity -buildWindows64Player`。
3. **Unity 端口路径**：`#if UNITY_EDITOR` 只区分了编辑器/打包，没有区分 Windows/Mac 平台分支。
4. **Python 子进程路径**：`PythonProcessLauncher`（v0.23.2 待加）里若写死 `python.exe` 则 Mac 上找不到。

但**架构本身是跨平台友好的**，核心依赖不存在 Windows 硬绑定：

- **kuzu 有 macOS wheel**：`uv.lock` 显示 kuzu 0.11.3 提供 `macosx_11_0_arm64.whl`（Apple Silicon）和 `macosx_11_0_x86_64.whl`（Intel），Python 3.11/3.12/3.13 均覆盖。这是最关键的 C 扩展依赖，已确认跨平台可用。
- **Unity 已配置 Mac 支持**：`ProjectSettings.asset` 里 `MacStandaloneSupport` 已在 `m_BuildTargetGraphicsJobs` 列表，说明 Unity 项目本身能切到 Mac 平台构建。
- **Python 业务代码无平台相关 syscall**：`main.py`、`servers.py` 等用的是 `asyncio`、`os.path`、标准库，无 Windows-only API。
- **协议层纯 Protobuf**：跨语言跨平台无障碍。

### 12.2 macOS 打包形态

是的，macOS 上不打 `.exe`，而是：

- **Unity 构建产物**：`-buildOSXUniversalPlayer` 产出 `.app` 包（可选 Universal Binary 同时含 arm64+x86_64）。
- **分发格式**：通常打成 `.dmg`（磁盘镜像）或 `.zip`（含 `.app`）。`.dmg` 更规范，玩家拖到 Applications 即装。
- **签名与公证**：macOS 上未签名/未公证的 `.app` 会被 Gatekeeper 拦截，玩家需右键打开或去「系统设置 > 隐私与安全」放行。正式发布建议做 Developer ID 签名 + 公证（需 Apple 开发者账号 $99/年）。

### 12.3 额外支持 macOS 的工作项与工作量

以下按「额外于 Windows 方案」的工作量估算。假设 Windows 方案（v0.23.0-v0.23.6）已完成。

| 工作项 | 内容 | 工作量 | 难度 |
|--------|------|--------|------|
| **A. Python 解释器跨平台** | v0.23.1 的 `build_python_runtime` 需额外下载 macOS 版 python-build-standalone（arm64 + x86_64），分别装依赖到 `runtime_mac_arm64/`、`runtime_mac_x86_64/`（或用 Universal2） | 0.5 天 | 低 |
| **B. 打包脚本跨平台** | `build_package.cmd` 是批处理，Mac 上不能跑。需新增 `build_package.sh`（bash）或改用跨平台脚本（Python/PowerShell Core）。`-buildWindows64Player` 换成 `-buildOSXUniversalPlayer` | 0.5 天 | 低 |
| **C. Unity 端口路径平台分支** | `AgentService.GetPort()` 的打包分支需区分 Windows/Mac。Mac 上 `Application.dataPath` 是 `<游戏>.app/Contents`，`Parent` 是 `.app`，再 `Parent` 是 `.app` 所在目录。需用 `#if UNITY_STANDALONE_OSX` 单独处理 | 0.5 天 | 中（需实测 Mac 路径） |
| **D. PythonProcessLauncher 跨平台** | v0.23.2 的 launcher 里 `python.exe` 改为按平台选 `python`（Mac）或 `python.exe`（Win）。`ProcessStartInfo.EnvironmentVariables` 在 Mac 上同样可用 | 0.5 天 | 低 |
| **E. macOS 构建机** | 需一台 macOS 机器做打包（Unity Mac 版 + Xcode）。Windows 打包机无法产 Mac 产物 | - | 基础设施 |
| **F. 打包产物目录结构** | Mac 上 `.app` 是包目录，PythonServer 应放 `.app/Contents/` 内或 `.app` 同级。路径关系与 Windows 不同，需重新设计 | 0.5-1 天 | 中 |
| **G. 签名与公证（可选但推荐）** | Developer ID 签名 + `xcrun notarytool` 公证。无签名也能跑，但体验差（玩家要手动放行） | 1 天 | 中（需 Apple 账号） |
| **H. `.dmg` 打包** | 用 `hdiutil` 或 `create-dmg` 工具把 `.app` 打成 `.dmg` | 0.5 天 | 低 |
| **I. 跨平台测试** | 在 Mac（arm64 + Intel）上跑完整验证清单（§11.3） | 1 天 | - |
| **合计** | | **约 5-6 人天**（不含等 Apple 账号审批） | |

### 12.4 建议

- **先完成 Windows 方案（v0.23.0-v0.23.6）**，跑通整套打包链路再考虑 macOS。跨平台改动大多是在现有脚本/代码上加平台分支，过早引入会拖慢 Windows 主线。
- **macOS 支持可作为 v0.24 单独立项**，工作量约一周。其中 C（端口路径）和 F（目录结构）是需要实测、容易踩坑的两点，其余多为脚本适配。
- **若只是个人/小范围分发，可跳过签名公证（G）**，玩家首次右键打开即可。正式公开发布再补。
- **Apple Silicon 与 Intel 双架构**：建议直接用 Universal Binary（`-buildOSXUniversalPlayer` + Universal2 Python），一份包通吃，避免维护两套。

### 12.5 关键风险

| 风险 | 说明 |
|------|------|
| Mac 上 `.app` 包路径结构 | `Application.dataPath` 在 Mac 下的层级与 Windows 不同，端口文件定位需实测，是最大不确定性 |
| python-build-standalone Mac 版兼容性 | 理论可用，但需实测 kuzu 的 macOS wheel 在内嵌解释器下能否正常加载 |
| 签名/公证流程 | 无 Apple 开发者账号则无法签名，玩家体验受影响（但不阻塞功能） |
| Mac 打包机依赖 | 必须有 macOS 机器，无法在 Windows 上交叉打包 Mac 产物 |
