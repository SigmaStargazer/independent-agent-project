## 1. 背景与目标

### 1.1 现状问题

v0.23.3a 采用「Python 内嵌运行时」方案：把完整 CPython 3.12（python-build-standalone）+ 全部依赖装进 `PythonServer/python/`，自包含、可整体拷贝。**开发者手动启动** `python/python.exe main.py`，Unity 再连接 TCP。

该方案解决了「玩家机器无 Python/uv」的问题，但存在缺陷：

1. **交付体量大**：整个 `python/`（解释器 + 依赖）要随安装包分发给玩家，体积大（数百 MB）。
2. **源码完全暴露**：业务代码以 `.py` 明文随包分发，玩家可读可改（见 `打包方案.md` §3.6）。
3. **结构不优雅**：安装包里带一个「python 目录」观感差、易被误删/杀软误报，且需要 Unity 侧有启动/生命周期管理逻辑。

### 1.2 用户诉求（v0.23.3b）

用户提出替代方向：

1. **把 Python 端打包为 exe，交给 Unity 托管启动** —— 避免把整个 Python 环境提供给用户。
2. **开发环境继续用 uv** —— 开发期保持 `uv` + venv 工作流，运行/交付形态与开发环境解耦。
3. **先验证该方案可不可行；并研究还有没有其他「不需要把 Python 环境提供给用户」的方案**。

## 2. 候选方案全景（不把 Python 环境给用户）

> 核心约束：玩家机器**不装 Python、不装 uv、不需要开发者手工配置任何环境**，运行期由 Unity 或系统自动拉起「大脑」。

| 方案 | 一句话 | 交付物 | 玩家机器依赖 | 源码保护 | 体积 |
|------|--------|--------|--------------|----------|------|
| **A. PyInstaller 打包 exe** | 把 `main.py`+依赖打成 exe，Unity `Process.Start` 拉起 | 单个/目录式 exe | 无 | 中（pyc+运行时，可反编译） | 中-大（约 100-300MB） |
| **B. Nuitka 编译原生 exe** | 把 Python 整体编译为 C 再链成 exe | exe + 依赖 dll | 无 | 高（原生代码） | 中-大 |
| **C. 内嵌运行时（现状 v0.23.3a）** | 带一个自包含 python/ 目录 | 目录 | 无 | 低（明文 py） | 大 |
| **D. py2exe / cx_Freeze** | PyInstaller 同类，目录式 | 目录式 exe | 无 | 中 | 中-大 |
| **E. 远程/云端大脑** | Python 跑在服务端，Unity 连远端 | 无本地 Python | 需要网络 | 高 | 极小 |
| **F. WebAssembly/Pyodide** | 浏览器/嵌入式里跑 Python | wasm | 需 JS 运行时 | 中 | 中 |
| **G. 单文件 exe（PyInstaller --onefile）** | A 的变体，全打一个文件 | 单 exe | 无 | 中 | 大且启动慢（解压） |

### 2.1 候选方案初筛

- **C（现状）**：是用户想摆脱的形态，不作为推荐，仅作对比基线。
- **F（WebAssembly/Pyodide）**：与 Unity 客户端（非浏览器）不匹配，且 kuzu/graphiti 是 C 扩展，Pyodide 跑不了 → **淘汰**。
- **E（云端）**：涉及服务端部署、联网依赖、数据隐私，且与「单机异步架构」定位冲突（当前 Python 与 Unity 同机 TCP）→ **本期不作为主选**，仅记录为长期替代方向。
- **A / B / D / G**：都是「本地 exe 化」，属同一技术族，差异在打包器与形态。**本期重点验证 A（PyInstaller，最主流）**，B（Nuitka）与 G（onefile）作为对照项。

### 2.2 本期重点验证对象

| 重点 | 方案 | 理由 |
|------|------|------|
| **主验证** | **A. PyInstaller 目录式（onedir）** | 最主流、生态成熟、对 kuzu 等原生扩展的 hook 支持较好；启动快（无解压） |
| 对照 1 | **G. PyInstaller 单文件（onefile）** | 交付物最干净（单个 exe），但启动慢、杀软误报率高，需对比 |
| 对照 2 | **B. Nuitka** | 源码保护最强，但 kuzu/graphiti 原生扩展兼容性是最大风险，成本高 |
| 兜底 | **C. 内嵌运行时（现状）** | 若 exe 路线不可行，退回现状，但需接受其缺陷 |

## 3. 关键风险点（决定 exe 路线是否可行的核心）

以下风险需在验证阶段逐一实证，任何一项不可解都可能推翻 exe 路线：

| # | 风险点 | 说明 | 影响 |
|---|--------|------|------|
| R1 | **kuzu C 扩展** | `kuzu 0.11.3` 是原生 `.pyd`（cp312-win_amd64），PyInstaller 需能收集到；动态加载（dlopen）场景易漏 | 高 |
| R2 | **graphiti_core 本地包** | 仓库内纯 Python 本地包（无 setup/pyproject），PyInstaller 默认按 import 图收集，需确认能打进 | 中 |
| R3 | **protobuf 命名空间包** | `protobuf==3.20.3` 的 `google` 命名空间包依赖 `.pth` 文件（v0.23.3a 已验证），PyInstaller 是否保留 | 中 |
| R4 | **运行时外部文件依赖** | `main.py` 依赖 `Data/Config/agent_server_port.txt`、`Lib/proto/`、`.env`、`db/`（Kuzu 图库可写） | 高（路径重构） |
| R5 | **.env / API Key 读取** | `main.py` 启动读 `.env` / `api_config.json`；打成 exe 后路径与文件分发方式变化 | 中 |
| R6 | **启动方式** | exe 由 Unity `Process.Start` 拉起，需能带参/写端口文件、可被干净退出；当前手动启动无此逻辑 | 中（开发阶段） |
| R7 | **kuzu 文件锁 / 数据目录** | Kuzu 图库 `db/graphiti.kuzu` 是运行时读写，exe 内不可写，必须外置到可写目录 | 高（路径重构） |
| R8 | **杀软误报** | PyInstaller 打包产物常被 Windows Defender / 第三方杀软误报 | 中（onefile 尤甚） |

## 4. 验证方案（如何实证可行性）

### 4.1 验证环境

- 平台：Windows x64（当前开发机）
- Python：`.venv`（uv 创建，当前 3.11.11）**或** 用 `python-build-standalone` 3.12（与 v0.23.3a 一致的 3.12）—— **验证结论需说明用哪个版本跑通**
- 打包工具：PyInstaller（需安装，验证阶段装进 venv 或独立环境）

### 4.2 验证步骤（按依赖递进）

**Step 0：准备打包环境**
- `pip install pyinstaller`（装进验证用环境）
- 确认 pyinstaller 版本

**Step 1：最小冒烟 —— 能打出可运行 exe**
- 用 `hello.py`（仅 print）→ PyInstaller onedir → 运行 exe 出结果
- 目的：确认 PyInstaller 工具链本身可用（排除环境问题）

**Step 2：核心依赖打包 —— 能收集到关键库**
- 打一个 `import kuzu, langchain_openai, langgraph, google.protobuf, graphiti_core` 的最小脚本 → 打包 → 运行 exe 能 import
- 目的：**验证 R1（kuzu C 扩展）、R2（graphiti_core）、R3（protobuf）** 能否被正确收集
- 若失败：尝试 `--collect-all kuzu`、`--collect-all graphiti_core`、`.spec` 手工加 data/binary

**Step 3：真实入口 —— main.py 能打包并启动**
- 把 `main.py` + 业务代码目录作为入口打包
- 目的：验证 R4/R5（外部文件依赖）—— exe 启动后能否找到 `agent_server_port.txt`、`.env`、`Lib/proto`、`db/`
- 预期难点：打包后的 `__file__`/`sys.path` 变化，相对路径失效 → 需临时验证「把外部资源放到 exe 同级目录」能否工作（不写死方案，只验证可行性）

**Step 4：真实启动 —— 监听端口 + 写端口文件**
- 运行打包后的 exe，验证：
  - 能监听 TCP 端口
  - 能写 `agent_server_port.txt`
  - 能正常响应一个最小请求（可复用 `CSharpClient` 或最小 TCP 客户端）
- 目的：证明「exe 替代 python.exe main.py」在功能上等价

**Step 5：对照项（可选，时间允许）**
- G. onefile 打包冒烟（对比体积/启动时间）
- B. Nuitka 仅评估不深做（记录风险）
