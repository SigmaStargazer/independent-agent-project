# 生命周期架构梳理（Architecture）

> **目录定位**：本文档是**跨版本**的架构梳理文档，描述本项目的生命周期（Lifecycle）架构原则与各系统归属。
> 版本化实现细节见对应版本的 `DevDocs/vX.Y/solution.md`（当前为 `DevDocs/v0.23.0b/solution.md`）。
> 本文档随架构演进同步更新，**不**随单个版本归档。

---

## 一、生命周期核心原则

本项目采用「**Title 零系统 → 进游戏初始化 → 回 Title 关闭**」的显式生命周期模型。

```
Title（零系统）──进游戏──► 游戏内（全系统运行）──回 Title──► Title（零系统）
      ▲                                                        │
      └──────────────再次进游戏（全新初始化）◄─────────────────┘
```

- **Title 阶段零系统**：不初始化 MemoryManager、AgentManager、EmbedderService、DBConnectionService、TimeSystem 等任何系统，仅保留 TCP 端口监听。
- **进游戏才初始化**：进入正式游戏场景（NewGame / ContinueGame）时显式初始化全部系统。
- **回 Title 就关闭**：回到 Title 时显式关闭全部系统，回到零系统状态。
- **幂等**：初始化和关闭均可重复调用，重复调用无副作用。

> 架构依据（**架构优先原则**，见 `AGENTS.md` 已确认约定第 0 条）：不以「最小改动」为目标，永远以架构最干净、最符合项目长期发展的实现方式为目标。生命周期采用显式「零系统 → init → close」闭环，而非热更新 / reinitialize。

## 二、各系统生命周期归属

### 2.1 Python 侧系统归属总表

> **初始化归属说明**：实际代码中 `enter_game()` 只直接调用 `MemoryManager().initialize()` 一行；`DBConnectionService` 与 `EmbedderService` 的初始化是 `MemoryManager.initialize()` **内部级联**完成的（`memory_manager.py` `initialize()` 中 `await DBConnectionService().initialize()` + `await EmbedderService().initialize()`）。因此「初始化归属」列用「入口 + 是否级联」区分。

| 系统 | 初始化入口 | 关闭归属 | 说明 |
|------|-----------|----------|------|
| **MemoryManager**（Graphiti/Kuzu） | `enter_game()` 直接调用 `initialize()` | `leave_game()` 直接调用 `close()` | 依赖 DB/Embedder，最晚初始化、最早关闭 |
| **DBConnectionService**（Kuzu 连接） | `MemoryManager.initialize()` **内部级联**（非 enter_game 直调） | `leave_game()` 直接调用 `close()` | 文件锁敏感，必须走完整 close 链 |
| **EmbedderService**（Embedding/Reranker） | `MemoryManager.initialize()` **内部级联**（非 enter_game 直调） | `leave_game()` 直接调用 `close()` | 需补 `close()`（v0.23.0b） |
| **AgentManager**（LangGraph Agent 池） | **无独立 initialize**（空容器；Agent 实例由后续 `acreate_agent` / `aload_agent_all` 填充） | `leave_game()` 直接调用 `aremove_all()` | 停止 Agent 始终执行（即使未初始化也要兜底清理） |
| **Agent LLM 缓存**（`_llm_with_tools`） | 首次使用时构建 | `leave_game()` 清缓存 | 需补 `reset_llm_cache()`（v0.23.0b），否则 Key 跨进出残留 |
| **TimeSystem**（虚拟时钟） | `SceneStart`（**不**在 enter_game） | `leave_game()` 归零 | 见 §2.2，特殊归属 |

### 2.2 TimeSystem 的特殊归属（已确认）

TimeSystem 是本地虚拟时钟（单例、进程内状态），不依赖 Key/Memory/Embedder，但与游戏生命周期绑定。

| 阶段 | 归属 | 动作 |
|------|------|------|
| **进程启动** | 无（**移除** `main()` 的 `aset_time`） | 不设置，Title 阶段 TimeSystem 完全零状态 |
| **进游戏** | `enter_game()` **设基准** + `SceneStart` **启动** | `enter_game`：`aset_time(2016,1,1)`（设虚拟时间基准，**不启动**）；`SceneStart`：`aset_speed(1440)` + `astart_time()` |
| **回 Title** | `leave_game()`（新增） | `TimeSystem().areset()`（暂停 + 归零） |
| **场景间清场** | `SceneStop`（现状不动） | 仅 `apause_time()` |

**关键点**：
- **时间「基准」在 `enter_game` 设置、时钟「启动」在 `SceneStart`**。原因（2026-08-21 修正）：Unity Flow 中 `CreateAgent`/`LoadAgent` 步骤在 `SceneStart` **之前**执行，创建/加载 Agent 时需调用 `aget_current_time()`（如 `EntityNode.created_at`），若基准未设置会拿到 `None` 导致报错。故 `enter_game` 先 `aset_time` 设好基准（时钟不走动），`SceneStart` 再 `aset_speed` + `astart_time` 真正启动。
- `SceneStart` 是所有进游戏 Flow（NewGame/ContinueGame/切关 NextMapFlow）的统一终点，时钟启动天然在这里。
- 回 Title 后 `ReturnToTitleFlow` 不再发 `SceneStop`（由 `CloseStep` 统一负责），`apause_time()` 不会被调用，因此 `leave_game` 必须用 `areset()` 兜底归零。

## 三、生命周期统一编排入口（AgentLifecycle）

Python 侧提供统一的生命周期编排模块 `AgentLifecycle`（`lifecycle/lifecycle.py`），进游戏 / 回 Title 都走它，避免逻辑散落在各 handler。

```python
class AgentLifecycle:
    @staticmethod
    async def enter_game() -> None:
        """进游戏：注入最新配置并全新初始化。幂等：已在游戏内则跳过。"""
        if MemoryManager().is_initialized:
            return
        load_api_config_into_env(force=True)   # 读最新 api_config.json 注入 env
        await MemoryManager().initialize()     # 内部 init dbsvc + embedder + graphiti + action_skill

    @staticmethod
    async def leave_game() -> None:
        """回 Title：停止 Agent、归零时间并关闭全部系统，回到零系统状态。幂等。"""
        await AgentManager().aremove_all()     # 1. 停止并移除全部 Agent（始终执行）
        reset_llm_cache()                      # 2. 清 Agent LLM 缓存
        await TimeSystem().areset()            # 3. 暂停并归零虚拟时间（始终执行）
        if not MemoryManager().is_initialized:
            return                             # 零系统状态，跳过资源关闭
        await MemoryManager().close()          # 4. 关 MM（worker/graphiti/driver）
        await DBConnectionService().close()    # 5. 关 Kuzu 连接
        await EmbedderService().close()        # 6. 关 Embedder/Reranker
```

**关闭顺序**：先 Agent（停止推理）→ 清 LLM 缓存 → 归零时间 → 再 Memory → DB → Embedder（资源依赖自内而外，避免 Kuzu 文件锁残留）。

**幂等语义**：
- `enter_game` 在已初始化时跳过（防重复 InitRequest）。
- `leave_game` 在未初始化时跳过资源关闭，但 **Agent 停止 / 时间归零始终执行**（防重复 CloseRequest 或从未进游戏的兜底清理）。

## 四、与 Unity Flow 的对应关系

| Flow | 生命周期行为 | 说明 |
|------|-------------|------|
| **NewGameFlow** | 开头 `StopAgent` → `InitializeStep`（enter_game）→ DeleteMemory → CreateAgent → … → StartAgent | 清场 → 初始化 → 新建记忆 → 启动 |
| **ContinueGameFlow** | 开头 `StopAgent` → `InitializeStep`（enter_game，幂等）→ RestoreMemory → … → StartAgent | 清场 → 初始化（Title 场景）或幂等跳过（关卡内 Retry）→ 恢复记忆 → 启动 |
| **ReturnToTitleFlow** | `CloseStep`（leave_game）→ LoadScene(title) | **关闭全部系统** → 回标题 |
| **NextMapFlow** | 不触发任何初始化/关闭 | 游戏内切关，系统保持运行（Interrupt → Backup → LoadScene → Start） |

### 4.1 关键设计点

- **`ContinueGameFlow` 双场景兼容（方案 A 已确认）**：`ContinueGame()` 有 3 个调用点——Title「继续游戏」（零系统）与关卡内 Retry 按钮（已初始化）。因 `InitializeStep` 幂等，同一 Flow 天然兼容两场景，无需拆分 `RetryGameFlow`（Retry 语义上就是「从最近存档恢复」= ContinueGame；拆分会产生几乎相同的 Flow，违背 DRY）。
- **`CloseStep` 取代 `StopAgentStep`（方案 X 已确认）**：`leave_game()` 内部完整负责「停止 Agent + 关闭全部系统」，ReturnToTitle 不再需要单独的 `StopAgentStep`，避免职责重叠。`SceneStopRequest` 仍保留，用于 NewGame/ContinueGame 开头的清场（那些场景只需停止 Agent、暂停时间，不需关闭系统）。

## 五、配置（API Key）生效机制

得益于「零系统 → 全新 init」模型，改 Key 生效**无需重启 Python 进程、无 reinitialize、无热更新**：

```
Title 保存 → api_config.json（明文）
   ↓
Title 点开始游戏 → InitializeStep → InitRequest → AgentLifecycle.enter_game()
   → load_api_config_into_env(force)   # 每次进游戏都读最新 json
   → MemoryManager.initialize()        # 全新初始化（新 Key）
   ↓
游戏内点「回标题」→ ReturnToTitleFlow → CloseStep → CloseRequest → AgentLifecycle.leave_game()
   → 停止 Agent + 时间归零 + close 全部 → 回零系统
   ↓
Title（再次零系统）→ 改 Key → 再进游戏 → 全新初始化 → 新 Key 生效
```

**核心**：因为每次进游戏都是「从零系统全新初始化」，每次都会重新读 `api_config.json`，所以 Key 改动在下次进游戏必然生效。架构上这是「零系统 → 全新 init」，**不是**热更新。

### 5.1 底层机制：`os.environ` 是唯一数据源（为什么无需重启进程）

关键认知：`load_api_config_into_env` 注入的是**进程内存里的 `os.environ` 环境变量表**，**不是** `.env` 文件。`.env` 只是启动时被 `load_dotenv()` 一次性读进 `os.environ` 的初始值，之后 `.env` 文件本身不再被读取。

```
进程启动  load_dotenv() ────────► os.environ（内存表）   初始值来自 .env
进游戏    load_api_config_into_env(force=True) ─► 覆盖   读最新 api_config.json
                 └─ os.environ["AGENT_API_KEY"] = <json 值>
运行时    os.getenv("EMBEDDING_API_BASE") ──► 读内存表   读到的是覆盖后的值
```

对应到代码：
- 启动时：`embedder_service.py:27` `load_dotenv()` 把 `.env` 读进 `os.environ`。
- 进游戏时：`lifecycle.py:35` `load_api_config_into_env(force=True)` 用 `api_config.json` **无条件覆盖** `os.environ`。
- 运行时构造：`embedder_service.py:62` `os.getenv("EMBEDDING_API_BASE")` 等——`os.getenv` 只读内存表，从不读文件。而它是在 `initialize()`（即 `enter_game` 的 `load_api_config_into_env` 之后）才被调用，所以读到的一定是最新 json 值。

因此「换 Key 无需重启进程」的本质：**每次 `initialize()` 构造 LLM/Embedder 时，`os.environ` 已被 `force=True` 刷新成最新 json 值**，而旧的构造实例在 `leave_game()` 时已销毁（`EmbedderService.close()` / `reset_llm_cache()`），无残留。

**何时需「回 Title 再进」而非立即生效**：仅当**游戏运行中**（已初始化）改 Key 时，`enter_game` 幂等跳过、已有实例持旧 Key，所以需回 Title（自动 `leave_game` 关闭）再进游戏才会用新 Key。这仍是「无需重启进程」——回到 Title 后系统已清零，再进即全新初始化。

**如何验证覆盖已完成**：
1. **看日志（推荐）**：进游戏时控制台打印 `[api_config] 已注入 N 项配置: [...]` + `[lifecycle] enter_game 完成，系统已初始化`，即证明 json 已覆盖 env 并完成初始化。
2. **临时断言**：在 `api_config_loader` 的 `os.environ[key] = value.strip()` 后临时加一行 `print` 打印实际值（注意只打印部分防泄露），验证后移除。

**边界**：`load_api_config_into_env` 对 **json 中为空** 的字段会跳过注入（`if not value`），此时 env 保留 `.env` / 环境原值——这是「json 未填则回退 .env」的设计，也是 Unity 侧 `UISetting.IsConfigReady()` 要求 12 项全填的原因。

## 六、协议支撑

| 消息 | 方向 | 用途 | 归属 handler |
|------|------|------|--------------|
| `InitRequest` / `InitResponse` | Unity → Python → Unity | 进游戏初始化（收敛到 `AgentLifecycle.enter_game()`） | `handle_init_request` |
| `CloseRequest` / `CloseResponse`（新增，field 34/11） | Unity → Python → Unity | 回 Title 关闭（`AgentLifecycle.leave_game()`） | `handle_close_request` |
| `SceneStopRequest` / `SceneStopResponse` | Unity → Python → Unity | 场景间清场（仅停止 Agent + `apause_time`） | `handle_scene_stop_request` |

三个消息职责区分：
- **InitRequest**：系统级「初始化」（进游戏）。
- **CloseRequest**：系统级「关闭」（回 Title）。
- **SceneStopRequest**：场景级「清场」（切关/开局前），不关闭系统。

- **v0.23.0a**：首个引入 Title API 配置 UI + 注入机制的版本。当时设计是「启动即 initialize + 报错才无 Key 模式」，存在「改 Key 需重启进程」「Title 阶段有初始化系统」的架构问题。
